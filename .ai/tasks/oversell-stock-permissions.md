# وضعیت فیچر: خالی‌فروشی/موجودی هوشمند — زنجیره مجوز + ارتباط صرفاً API

## سند راه‌حل (solution-architect)

**مسئله** (درخواست کاربر 2026-09-28):
1. فیلدهای نقطه سفارش/حداقل موجودی/خالی‌فروشی به صفحه تعریف و ویرایش محصول
   داشبورد فروشگاه اضافه نشده بود — بررسی نشان داد DTO/lib/API و اعمال در
   placeOrder از دور ۱۳-۱۴ موجودند ولی **UI فیلدها در ProductForm هرگز رندر
   نمی‌شود** (مدل فرم و body پر می‌شود، input ندارد).
2. گزینه خالی‌فروشی باید در نقش‌های کاربران **هر دو سمت** (پنل Core و
   داشبورد فروشگاه) به‌صورت مجوز قابل واگذاری بیاید، با این زنجیره:
   کارشناس دامنه (نقش Core با مجوز) → فعال‌سازی خالی‌فروشی + سقف کل فروشگاه
   در تعریف دامنه → مالک فروشگاه این مجوز را فقط وقتی لایسنس فعالش کرده در
   لیست نقش‌ها می‌بیند و به کارشناس محصول می‌دهد → کارشناس محصول در فرم
   کالا خالی‌فروشی هر محصول را ۱ تا سقف آلازکور تنظیم می‌کند.
3. همه تبادل دیتا بین پنل Core و داشبورد فروشگاه باید از **API** باشد —
   خواندن مستقیم دیتابیس ممنوع. یافته‌ها: `core/lib/site-queries.ts` (۴
   گزارش) و `core/lib/usage.ts` (قاعده در-حال-استفاده) دیتابیس سایت‌ها را
   مستقیم با PrismaClient خام باز می‌کردند.

**پشته**: Node.js/Next.js (هر دو اپ shop و core) + Mantine 8 + SQLite/Prisma —
همان پشته موجود.

**طرح**:

- «قابلیت» (capability) — نوع جدید مجوز کنار منوها؛ یک رشته در همان آرایه
  permissions: `/products:oversell` (فروشگاه) و `/panel/domains:oversell`
  (Core). در مجموعه اعتبارسنجی نقش‌ها (ASSIGNABLE_PERMISSIONS /
  CORE_PERMISSIONS) اضافه می‌شود؛ helper.hasCapability، ادمین/'*' همیشه مجاز.
- Core: فرم دامنه فیلدهای خالی‌فروشی را فقط با مجوز نشان می‌دهد؛ API
  domains POST/PATCH اگر فیلد خالی‌فروشی در payload باشد و مجوز نباشد → 403.
- Shop: صفحه نقش‌ها بخش «توانایی‌های ویژه» را فقط وقتی
  `license.oversell.allowed` است نشان می‌دهد؛ API محصول (POST/PATCH) تنظیم
  فیلدهای خالی‌فروشی را فقط با (لایسنس مجاز + مجوز نقش) می‌پذیرد و سقف کالا
  را به بازه ۱..حد دامنه clamp می‌کند؛ ویرایش بدون فیلد = حفظ تنظیم موجود.
- فرم محصول: نقطه سفارش/حداقل موجودی برای هر ویرایشگر کالا؛ بخش خالی‌فروشی
  فقط با (لایسنس مجاز + مجوز نقش).
- API-only سمت فروشگاه: `/api/core/reports/[kind]` (products، product-sales،
  monthly-sales، sales، categories — روی lib/reports.ts خود سایت) و
  `/api/core/integration-usage` (تشخیص در-حال-استفاده درگاه/پیامک با
  AppConfig + OnlinePaymentTransaction). احراز با هدر `x-core-key` = کلید
  Core (همان اعتماد دوطرفه) و اتصال دامنه با هدر `x-site-domain`؛ پراکسی
  فروشگاه مسیرهای api را از گیت نشست معاف می‌کند.
- Core: `core/lib/shop-api.ts` (SHOP_API_URL با پیش‌فرض 127.0.0.1:3000 +
  resolveApiKey) و بازنویسی درونی site-queries/usage روی HTTP با حفظ امضای
  عمومی (صفحات گزارش و اکسل دست‌نخورده). استثنا: `core/lib/provision.ts`
  زیرساختِ ساخت دیتابیس است نه تبادل دیتا.

**Edge Caseها**: مجوز ثبت‌شده با لایسنس بعداً غیرفعال = بی‌اثر (گیت محصول هم
لایسنس می‌خواهد)؛ Core در دسترس نبود در usage → null یعنی حذف نکن (همان
fail-safe قبلی)؛ پورت‌های متفاوت dev با SHOP_API_URL قابل تنظیم؛
ویرایشگر بدون مجوز هرگز نمی‌تواند تنظیم خالی‌فروشی موجود را پاک یا دور بزند.

**معیار پذیرش**: کارشناس Core بدون مجوز neither می‌بیندnor می‌تواند ست کند؛
مالک فقط با لایسنس فعال مجوز را در نقش‌ها می‌بیند؛ کارشناس محصول بدون مجوز
بخش خالی‌فروشی فرم را نمی‌بیند و API هم 403 می‌دهد؛ گزارشات Core و قاعده
در-حال-استفاده بدون هیچ دسترسی فایلی به دیتابیس سایت‌ها کار می‌کنند.

## بازبینی امنیتی + sign-off تک‌لید (2026-09-28)

**security-reviewer**: بدون P0/P1. اصلاح‌شده در همان دور:
- P2: فضای نام قابلیت‌ها به `cap:product-oversell` / `cap:domain-oversell`
  تغییر کرد — رشته قدیمی `/products:oversell` در قاعده view رشته‌های
  hasMenuPermission مشتاقِ مشاهده منو بود؛ `cap:` هرگز با href منو
  تطبیق نمی‌یابد (فروشگاه: کارشناس بدون grant /products دیگر دید لیست
  محصول از مجوز خالی‌فروشی نمی‌گیرد؛ Core: مشکل PII بین‌مستأجری رفع شد).
- P3: مقایسه ثابت‌زمانه کلید (timingSafeEqual) در هر دو مسیر
  `/api/core/*` + پیام ۵۰۰ ژنریک (جزئیات فقط در لاگ سرور).
- P3: grantهای مرده زیرصفحه‌ها — matchingHref حالا طولانی‌ترین تطبیق را
  برمی‌گرداند و دو صفحه موجودی re-check داخل صفحه دارند.
- P3 پذیرفته‌شده (ثبت‌شده): race سقف‌های خالی‌فروشی پیش از $transaction —
  دو خرید همزمان می‌تواند سقف را اندکی رد کند (فقط جهت فروش بیشتر)؛
  rate-limit روی /api/core/* هنوز نیست.

**tech-lead**: «CHANGES-REQUESTED» با یک باگ کارکردی — رفع شد:
- **باگ قطعی خالی‌فروشی جزئی** در placeOrder: `allowNegative = shortfall
  >= item.qty` جبری یعنی stock ≤ 0 — خریدِ بیشتر از موجودیِ باقی‌مانده
  (مثلاً موجودی ۳، خرید ۵) با اینکه همه چک‌های سقف رد می‌شد، در تراکنش با
  شرط gte رد می‌شد و پیام غلط «موجودی در لحظه ثبت تغییر کرد» می‌داد.
  اصلاح: `allowNegative = shortfall > 0` + حذف کد مرده productRow.
  دود: موجودی ۲ → خرید ۵ → **۲۰۱، موجودی -۳** ✓ (سناریوی اصلی تسک کاربر).
- کامنت‌های قدیمی فضای نام به cap: به‌روز شد.

**تسویه نهایی**: typecheck هر دو اپ صفر؛ jest ۴۴/۴۴؛ بیلد سبز؛ گزارش
اکسل با دور ۱۵ بازتولید شد (scripts/build-task-report.ts). سرورهای
پروداکشن هر دو اپ روی 3000/3100 با بیلد نهایی در حال اجرا گذاشته شدند.

**پیشنهاد بعدی (غیرمسدودکننده)**: fan-out موازی گزارشات سایت‌ها در
site-queries (الان ترتیبی، هر سایت timeout ۶s)؛ 400 روی payload جزئی
خالی‌فروشی (فقط oversellMax بدون oversellAllowed)؛ rate-limit
/api/core/*؛ حذف redirect خودارجاعی دو صفحه موجودی به /dashboard.
