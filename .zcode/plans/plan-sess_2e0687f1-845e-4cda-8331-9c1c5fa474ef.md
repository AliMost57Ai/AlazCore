# پیاده‌سازی فرآیند تیکتینگ نسخه مرجع (TicketingSys) در پروژه فعلی

## یافته کلیدی اکتشاف
پروژه فعلی از قبل تیکتینگ پایه دارد اما ساده‌تر از نسخه مرجع است:
- **مشتری↔مالک**: `/account/support` + پنل `/customer-support` (مدل SupportTicket/SupportTicketMessage؛ ۴ وضعیت با «pending»، بازگشایی خودکار با پیام، بدون مهمان/ویجت/خوانده‌نشده/displayId/تنظیمات)
- **مالک↔کور**: `/support` (پروکسی با x-core-key) + `/panel/tickets` بک‌آفیس کور (مدل Ticket/TicketMessage؛ بدون polling/خوانده‌نشده/displayId)

نسخه مرجع فرآیند کامل دارد: **تیکت مهمان با کوکی، ویجت شناور چت با تنظیمات، خوانده/نخوانده مشتق از timestamp، displayId «TK-#####»، چرخه ۳ وضعیتی، پنل پشتیبان با جست‌وجو/فیلتر نخوانده/Context مشتری، سقف ۵ تیکت باز، شمارنده زنگ‌اخبار، polling**. نسخه مرجع سمت کور ندارد → همین فرآیند به جریان مالک↔کور تعمیم داده می‌شود.

## تصمیم‌های کلیدی (پیشنهادی — لطفاً در بازبینی تایید/تغییر دهید)
1. **چرخه وضعیت = ۳ حالته مرجع**: پیام درخواست‌کننده (مشتری/مالک سایت) → «در انتظار پاسخ» (open)؛ پیام پشتیبان (مالک/کور) → «پاسخ داده شده» (answered)؛ تیکت بسته = قفل برای پیام درخواست‌کننده (خطای فارسی) و بازگشایی فقط با اکشن صریح پشتیبان. وضعیت فعلی «pending» حذف و رکوردهای موجود به open نگاشت می‌شوند.
2. **حذف اولویت**: مرجع آگاهانه اولویت ندارد («اولویت تیکت وجود ندارد»). پیشنهاد: حذف ستون priority از هر دو مدل + UI. (جایگزین کم‌خطرتر: نگه‌داشتن ستون، حذف فقط از UI)
3. **UI مشتری = چت مرجع**: جایگزینی لیست پنلی فعلی مشتری با SupportChat مرجع (intro مهمان / فهرست / گفتگو / جدید) + ویجت شناور در خانه و صفحه محصول. کامپوننت‌های ژنریک برای دو سمت پنل حفظ و توسعه می‌یابند.
4. قراردادهای فعلی حفظ می‌شود: load-all بدون pagination، PanelList، فرم >۴ فیلد = صفحه اختصاصی، جزئیات موبایل = صفحه.

## تغییرات دیتابیس (db-architect)
**Shop — `prisma/schema.prisma` → SupportTicket:** افزودن `displayId @unique`، nullable شدن `userId` + `guestName/guestPhone/guestToken @unique`، `lastMessageAt`، `lastMessageAuthor`، `customerReadAt`، `staffReadAt`؛ حذف `priority`؛ ایندکس status/lastMessageAt؛ migration شامل `UPDATE pending→open`.
اعمال: `yarn db:site-migration` → `prisma/site-migrations/0002_ticketing_process.sql` + بازتولید site-schema.sql؛ سپس `yarn db:migrate-sites`؛ entrypoint داکر و provision کور خودکار آن را می‌گیرند.
**Core — `core/prisma/schema.prisma` → Ticket:** `displayId @unique`، `lastMessageAt/lastMessageAuthor`، `coreReadAt/tenantReadAt`؛ حذف priority؛ اعمال با `prisma db push`.
⚠️ تغییر مخرب بالقوه (drop priority + بازسازی جدول SQLite برای nullable شدن userId) — طبق قاعده با تایید همین پلن انجام می‌شود و قبل از مایگریشن از data/sites بکاپ گرفته می‌شود.

## معیار پذیرش
1. مهمان در خانه/صفحه محصول از ویجت با نام+موبایل تیکت می‌زند → TK-##### ساخته می‌شود، کوکی ست می‌شود، گفتگو در دسترس است؛ پاسخ پشتیبان → بج نخوانده ویجت.
2. مشتری: لیست/گفتگو با بج نخوانده؛ سقف ۵ تیکت باز؛ پیام روی تیکت بسته → خطای فارسی؛ بازگشایی فقط توسط پشتیبان.
3. پنل فروشگاه: جست‌وجو/فیلتر نخوانده/AutoRefresh/displayId؛ باز کردن جزئیات = markRead؛ Context فقط-خواندنی؛ زنگ‌اخبار = شمار نخوانده.
4. وضعیت‌ها: پیام مشتری→«در انتظار پاسخ»، پاسخ پشتیبان→«پاسخ داده شده»؛ بسته قفل است.
5. تنظیمات: ۷ کلید ذخیره و اعمال؛ خاموشی → ویجت مخفی + API فروشگاهی 403 + پنل بدون تاثیر.
6. مالک↔کور: تیکت مالک در پنل کور با displayId/نخوانده؛ پاسخ کور→answered؛ قفل/بازگشایی متقارن؛ سایت تعلیق‌شده اجازه تیکت ندارد.
7. مایگریشن بدون از دست رفتن تیکت‌ها؛ provision سایت تازه ستون‌های جدید را دارد.
8. `npm test` سبز (prettier/lint/typecheck/jest) و فرمتر روی فایل‌های تغییریافته.

## ریسک‌ها / حساسیت‌های امنیتی
- **Endpoint مهمان = نوشتن ناشناس**: سقف بر اساس guestToken، سقف طول subject/body، کوکی httpOnly/secure در prod؛ نام نویسنده همیشه از هویت سمت سرور (هرگز از body)؛ IDOR: دسترسی به [id] فقط با userId یا guestToken، وگرنه 404.
- هاردنینگ: مقایسه x-core-key با timingSafeEqual در tenant API.
- XSS: بدنه پیام فقط Text با pre-wrap، بدون HTML خام.
- بازسازی جدول SQLite (nullable userId / drop priority): بکاپ data/sites قبل از مایگریسن + تست روی کپی.
- polling همه‌جا visibility-gated؛ بدون pagination مطابق قرارداد ریپو (ریسک حجم در سند ثبت می‌شود).
