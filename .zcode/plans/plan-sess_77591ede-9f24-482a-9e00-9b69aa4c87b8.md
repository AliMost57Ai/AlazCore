# گیت کور + tenant دیتابیس + مایگریشن سایت‌ها + env توسعه/تولید + اعتبارنامه ادمین

## ریشه مشکل (بررسی کد)

سمت کور کامل است: `core/lib/licensing.ts:51` دامنه‌ی ثبت‌نشده/غیرفعال/تعلیق/منقضی را `ok:false` می‌کند. مشکل در سمت فروشگاه است که در چهار مسیر از این گیت رد می‌شود:

1. **Core تنظیم نشده = گیت غیرفعال** — `lib/core-license.ts:94` بدون env کور null برمی‌گرداند و سایت بدون تأیید لود می‌شود.
2. **گیت فقط روی صفحات** — matcher پراکسی (`proxy.ts:152`) همه‌ی `/api` را مستثنا می‌کند؛ حتی `/api/auth/login` بدون اعتبارسنجی کار می‌کند.
3. **Fallback بی‌صدا به app.db** — `lib/db.ts:59`: دامنه‌ای که فایل دیتابیسش نیست → `data/app.db` (دسترسی با IP/localhost یا nginx بدون `proxy_set_header Host $host` ⇒ همه ترافیک → app.db).
4. **SHOP_DOMAIN حتی در production** — `lib/site-context.ts:36`، `proxy.ts:55`، `core-license.ts:168`؛ docker.env فعلی joghd.ir دارد ⇒ همه درخواست‌ها به یک دیتابیس.

دو کمبود دیگر: (۵) تغییر schema بین پابلیش‌ها فقط با «لیست هاردکد» در `ensureSiteDb` (`lib/site-db.ts:146-306`) روی دیتابیس‌های موجود اعمال می‌شود — مایگریشن داده‌محفوظ و اسکریپتی ندارد؛ (۶) ادمین پیش‌فرض موقع provision ساخته نمی‌شود و اعتبارنامه در پنل کور دیده نمی‌شود.

## طراحی (سند solution-architect)

پشته: Node.js/Next.js هر دو اپ + SQLite — بدون تغییر schema دامنه/پلن؛ فقط یک جدول سیستمی `_SiteMigration` داخل دیتابیس هر سایت.

### ۱) گیت اجباری کور در production — «اول اعتبارسنجی، بعد لود»

ترتیب هر درخواست در production: resolve دامنه از Host → **اعتبارسنجی وجود/اعتبار از کور** (`/api/validate` موجود، بدون تغییر) → چک فایل دیتابیس سایت → لود سایت.

- matcher پراکسی به `/api` گسترش می‌یابد (به‌جز `/api/core/*`)؛ دامنه‌ی مسدود/ثبت‌نشده روی API ⇒ JSON 503. منطق session/redirect صفحات برای API اجرا نمی‌شود.
- **Core تنظیم‌نشده در production** = مثل «کور در دسترس نیست» (`failModeValue`): با closed مسدود، با open باز (اختیار اپراتور). کامنت `lib/core-license.ts:11-12` به‌روز می‌شود.
- `CORE_FAIL_MODE` پیش‌فرض docker.env.example → `closed` (قرارداد محصول).
- `/api/core/*` از گیت لایسنس مستثنا (کور مدیر سامانه است و باید گزارش دامنه‌ی تعلیق‌شده را هم بگیرد) ولی دامنه را بعد از احراز x-core-key صریح از هدر `x-site-domain` می‌خواند.
- توسعه (localhost/dev) مستثنا — «حالت تست راحت» فعلی حفظ می‌شود.

### ۲) ماتریس resolve دامنه — تابع مرکزی در `lib/site-runtime.ts`

| محیط | Host | SHOP_DOMAIN | نتیجه |
|---|---|---|---|
| dev | هرچه | ست | SHOP_DOMAIN (بی‌توجه به آدرس) |
| dev | localhost | خالی | null → app.db (حالت تست) |
| prod | دامنه واقعی | هرچه | **Host** (SHOP_DOMAIN نادیده + warn) |
| prod | localhost/IP | ست | SHOP_DOMAIN (سرور تست/healthcheck) |
| prod | localhost/IP | خالی | fail-closed → /site-inactive |

مصرف‌کننده‌ها همه به همین تابع: site-context.ts، proxy.ts، core-license.ts، layoutها (`app/(app)/layout.tsx:39`، `app/site-inactive/page.tsx:35`). هدر `x-site-domain` از زنجیره‌ی resolve عمومی **حذف** می‌شود (فورج آن انتخاب دیتابیس دلخواه می‌داد) — ALS پراکسی که حالا همه‌ی مسیرها را می‌پوشاند جایگزین مطمئن است.

### ۳) Fail-closed دیتابیس در production

- ساخت on-demand دیتابیس فقط dev (`ensureSiteDb(domain, { allowCreate })`)؛ در prod فقط ثبت دامنه در کور دیتابیس می‌سازد.
- prod + دامنه بدون فایل دیتابیس ⇒ صفحات: /site-inactive؛ APIها: SiteUnavailableError/503 — **هرگز app.db** (نشتی داده‌ی پنهان هم بسته می‌شود).
- باگ جانبی: `__siteEnsureInflight` (`lib/db.ts:51`) بعد از شکست پاک نمی‌شود — اصلاح می‌شود.

### ۴) مایگریشن خودکار و داده‌محفوظ دیتابیس‌های سایت (جدید)

- **تولید اسکریپت در توسعه**: بعد از تغییر `prisma/schema.prisma`، اسکریپت کمکی `scripts/new-site-migration.ts <نام>` با `prisma migrate diff --from-file prisma/site-schema.sql --to-schema-datamodel prisma/schema.prisma --script` فایل `prisma/site-migrations/NNNN_نام.sql` می‌سازد و `site-schema.sql` (وضعیت تجمعی) را بازتولید می‌کند. اگر diff شامل DROP/تغییر مخرب باشد هشدار می‌دهد — مایگریشن‌های مخرب قبل از کامیت بازبینی دستی می‌خواهند (پیش‌فرض: فقط افزودنی).
- **اعمال‌کننده مشترک** `lib/site-migrations.ts`: جدول `_SiteMigration` (نام فایل‌های اعمال‌شده)؛ هر فایل در یک تراکنش SQLite اجرا و ثبت می‌شود؛ idempotent.
- **سه نقطه‌ی اعمال**:
  1. اسکریپت CLI `scripts/migrate-sites.ts` — روی همه‌ی `data/sites/*/*.db` مایگریشن‌های pending را اعمال می‌کند؛ در `docker/entrypoint.sh` **قبل از next start** اجرا می‌شود (مایگریشن اتوماتیک هنگام پابلیش) و روی سرور هم قابل اجرای دستی است (`docker exec`).
  2. fallback داخل `ensureSiteDb` — هر دامنه‌ای که از قلم افتاده باشد در اولین تماس به‌روز می‌شود.
  3. provision کور برای دیتابیس نو، همه‌ی فایل‌های موجود را از ابتدا «اعمال‌شده» ثبت می‌کند (با site-schema.sql تجمعی هم‌خوان است).
- لیست هاردکد فعلی `ensureSiteDb` به فایل `0001_*.sql` تبدیل و از کد حذف می‌شود (با حفظ گاردهای idempotency فعلی، چون روی دیتابیس‌های قدیمی یک‌بار اعمال می‌شود).

### ۵) Provision کامل در کور + نمایش اعتبارنامه ادمین

- `core/lib/provision.ts`: علاوه بر schema، ادمین پیش‌فرض همان‌جا INSERT می‌شود (admin@{دامنه} با همان ثابت‌های salt/hash — raw SQL) + ساخت فایل tmp و rename اتمیک.
- `lib/site-db.ts`: بوت‌استرپ ادمین به `bootstrapSiteAdmin` مستقل استخراج می‌شود (شبکه‌ی ایمنی دیتابیس‌های قدیمی می‌ماند).
- API فروشگاه `app/api/core/site-admin` (x-core-key + x-site-domain): GET → {email, isDefaultPassword}؛ POST {action:'reset'} → بازگرداندن رمز به پیش‌فرض.
- API پروکسی کور `core/app/api/domains/[id]/site-admin` با requireApiMenu edit.
- **UI**: کارت «اطلاعات ورود فروشگاه» در صفحه ویرایش دامنه با الگوی Code+CopyButton (`SettingsClient.tsx:79`)، هشدار «رمز پیش‌فرض را تغییر دهید»، دکمه بازنشانی با تایید، badge dbStatus؛ بعد از **ایجاد** دامنه به‌جای لیست به همین صفحه هدایت می‌شوید. رمز پیش‌فرض admin1234 می‌ماند (تغییرش دست مالک است؛ reset برای بازگشت).

### ۶) جداسازی env + کش ۱۵ دقیقه‌ای لایسنس

- `CACHE_TTL_MS` به **۱۵ دقیقه** و قابل تنظیم با env `LICENSE_CACHE_TTL_SEC` (پیش‌فرض 900). کش منفی ۱۵ ثانیه‌ای Core-قطع سر جایش است. **پیامد اعلام‌شده**: تعلیق/انقضای دامنه حداکثر ۱۵ دقیقه بعد در فروشگاه اعمال می‌شود — ترجیح شما بر کاهش فشار validate.
- `docker.env.example`: حذف SHOP_DOMAIN (production = فقط Host؛ nginx باید `proxy_set_header Host $host` داشته باشد) + CORE_FAIL_MODE=closed + پیشنهاد SEED_ON_FIRST_BOOT=false.
- `.dockerignore`: الگوی `.env.*`؛ `.env` دست‌نخورده (با gate کد فقط dev/test اثر دارد).
- `docker-compose.joghd.yml` (container per-domain با SHOP_DOMAIN) حذف + بازنویسی بخش 13 DOCKER.md به «چند دامنه روی یک container» + مستند مایگریشن.

## معیار پذیرش
1. dev/localhost + SHOP_DOMAIN=shop2.ir ⇒ ورود admin@shop2.ir و داده از `data/sites/shop2.ir/shop2.ir.db`
2. prod: دامنه‌ی ثبت‌نشده ⇒ /site-inactive؛ API همان دامنه ⇒ 503 JSON؛ Core قطع + closed ⇒ هیچ صفحه/APIی لود نمی‌شود
3. prod: دامنه‌ی معتبر ⇒ دیتابیس خودش؛ دامنه‌ی معتبر بدون فایل DB ⇒ /site-inactive؛ هدر جعلی x-site-domain بی‌اثر
4. تغییر schema در توسعه ⇒ فایل مایگریشن تولید می‌شود؛ بعد از پابلیش، boot script همه‌ی دیتابیس‌ها را بدون حذف داده به‌روز می‌کند؛ اجرای مجدد بی‌اثر (idempotent)
5. ثبت دامنه در کور ⇒ فایل DB + ردیف admin@{دامنه} بلافاصله؛ اعتبارنامه در صفحه ویرایش دیده/کپی/بازنشانی می‌شود
6. کش لایسنس ≥۱۵ دقیقه (env قابل تنظیم)؛ docker.env.example بدون SHOP_DOMAIN و با closed؛ build + healthcheck + `npm run test` سبز
