## What this is

A Persian (RTL) e-commerce **storefront + admin panel** built on the Mantine Next.js App Router template. All user-facing text, UI labels, seeded data and API error messages are Persian. `<html lang="fa" dir={dir}>` reads the `mnt_dir` cookie so RTL is correct on the first paint (`app/layout.tsx`); Vazirmatn is the UI font.

Two files will mislead you if you trust them by name:

- **`README.md` is the untouched upstream Mantine template README.** It documents the starter, not this app.
- **`DEPLOY.md` (Persian) is the real deployment guide** — PM2/systemd, nginx + certbot, `VACUUM INTO` SQLite backups.

## Architecture

### Two surfaces, one app

| Surface | Where | Guard |
| --- | --- | --- |
| Admin/staff panel | `app/(app)/**` | `requireSession()` in the group layout + menu permissions |
| Customer account | `app/account/**` | session, role `customer` |
| Storefront | `app/page.tsx`, `app/shop/**` | public |
| Auth | `app/login`, `/login-otp`, `/signup`, `/forgot` | public |
| Payment link | `app/pay/[token]` | public capability token |
| API | `app/api/**` (46 route handlers) | each route authenticates itself |

The `(app)` route group is the admin panel: every page sits behind the session guard in `app/(app)/layout.tsx`, which also bounces `role === 'customer'` back to the storefront.

### Auth is three layers, deliberately

Next.js 16 renamed middleware to **Proxy** — the root-level `proxy.ts` is this project's middleware. It `matcher`-excludes `api`, `_next/*` and static files, so **every API route must call an auth helper itself**.

1. `proxy.ts` — optimistic redirects only (reads the signed cookie, never the user record).
2. Server layouts/pages — authoritative `requireSession()` / `canAccessMenu()` (`lib/auth.ts`). Middleware is not trusted; a page must not render because a cookie merely existed.
3. API routes — `requireApiUser` / `requireApiAdmin` / `requireApiMenu` from `lib/api-auth.ts`, which return `NextResponse` (401/403 JSON) rather than redirecting. Usage: `const s = await requireApiX(); if (s instanceof NextResponse) return s;`

Sessions are stateless HMAC-SHA256 tokens (`lib/session.ts`) built on Web Crypto + `btoa`/`atob` only, so the identical code runs in the Proxy (Edge) and in Node. **Never import `node:crypto` into `lib/session.ts`** or `proxy.ts` stops working. `AUTH_SECRET` is required in production (≥16 chars) and has a dev-only fallback. `lib/constants.ts` holds cookie names/TTLs separately so client components don't pull the signing logic into the browser bundle.

### Roles and menu permissions

`User.role` stores a machine name. Built-ins — `admin`, `member`, `customer` — are referenced by code; admin-defined rows live in the `Role` table (`isAdmin` grants full access, otherwise staff-level).

`lib/nav-permissions.ts` is the **single catalog** for panel access: `ASSIGNABLE_MENUS` (grantable hrefs grouped like the sidebar), `ADMIN_ONLY_HREFS` (user/role management, logs, credential-heavy settings), `ALWAYS_VISIBLE_HREFS`. It is deliberately free of React, icons and Prisma so the same constants load in the Proxy, server components, API routes and the client nav. **When you add a panel page, add its href here** and keep it in sync with `components/layout/nav-items.ts`.

Permissions are a **snapshot signed into the session at login** (`perms`), so role edits only take effect after the affected user signs in again. Admins are exempted via `effectivePermissions()` rather than by materialising `['*']` into the token.

### Payments — wallet-first

`lib/gateways/registry.ts` is the single source of truth: one descriptor per gateway (ZarinPal, IdPay, Parsian, Mellat, Saman, Sadad, Sepah, SizPay, Pasargad + BNPL: DigiPay, SnappPay, Tara, Vibe, Keepa, MiniPay, Fakher) with `isReady(settings)` / `start(ctx)` / `verify(ctx)`. **Adding a gateway = write a driver in `lib/gateways/` returning the `GatewayStartResult`/`GatewayVerifyResult` shape and add one descriptor entry.** Do not reintroduce per-gateway `switch` statements in routes — the registry replaced exactly that.

`lib/gateways/types.ts` holds the shared context/result types plus the HTTP helpers (`postJson`, `postFormJson`, `postSoap`, `xmlEscape`, `soapTag`). Drivers stay independent of Prisma and of the HTTP routes: they take a context object and return plain results.

Money flow: the gateway **always credits the wallet first** (`lib/wallet.ts`), then the order is paid from the wallet. `app/api/payment/callback/route.ts` is the one callback for every gateway — it handles GET redirects and form/JSON POSTs, and identifies the pending transaction by whichever id the gateway echoed back (`ID_KEYS`: `authority`, `token`, `orderid`, `trackingcode`, …). It is public on purpose: the gateway knows nothing about our session cookie, and the stored identifier is only accepted together with a successful verify against the exact stored amount. `OnlinePaymentTransaction` is the attempt ledger (pending *and* failed); `WalletTransaction` is the money ledger; `User.walletBalance` mirrors the ledger.

### Settings, themes, and the SQLite JSON-string convention

`lib/settings.ts` stores `AppSettings` (gateway + SMS credentials, active/default selections) in the `AppConfig` key-value table, data-driven through `FIELD_SPECS` — adding a field means adding one spec entry, and `getAppSettings`/`saveAppSettings` stay generic. Secrets live in the DB on purpose (`data/app.db` is gitignored and server-only) and reach the browser only through the admin-gated `/api/admin/settings`.

Storefront theming: `lib/themes.ts` defines four themes (`beautyshop`, `digimarket`, `digishop`, `softkala`), each an identity + 5-slot palette + togglable section list; `lib/theme-settings.ts` persists one `ThemeConfig` row per theme with `active` singling out the live skin; `components/themes/` renders them.

**SQLite has no native `Json` column**, so structured data is stored as JSON strings parsed and validated in lib code: `Product.props`, `Product/Category.placements` (`{ themeId: [sectionId] }` pins), `Order.itemsJson`, `Role.permissions`, `ThemeConfig.config`, `MetaTag.content` (allowlisted kinds/IDs only — never arbitrary scripts). The `datasource url` is hardcoded to `file:../data/app.db` on purpose so CLI, seed and runtime resolve the same file with zero `.env` setup.

### Conventions that are load-bearing

- **Hydration safety over convenience.** `lib/format.ts` deliberately avoids `Intl.NumberFormat('fa-IR')` and hand-rolls Persian digits/separators, and orders store a pre-formatted Jalali date *string*. Node and browser ICU data can differ, and any difference shows up as a React hydration mismatch. Keep new date/number formatting pure string work.
- **Split client-safe modules from server ones.** Constants and pure logic live in Prisma-free, React-free modules so client components can import them without dragging the DB into the bundle — compare `lib/order-status.ts` (safe) with `lib/orders.ts` (Prisma), `lib/constants.ts` with `lib/session.ts`, and `lib/price-adjust.ts`. Place new code on the correct side of that line.
- **Comments explain why, often in Persian.** The codebase is densely commented with rationale (schema fields, gateway quirks, "kept local to avoid importing…"); match that density and explain intent, not mechanics.
- Money is integer **Toman**; `Order.itemsJson` snapshots each line's `unitPrice` at order time so price changes never rewrite sold invoices (see `PriceChange`).

### Testing

Jest + React Testing Library, colocated (`lib/format.test.ts`, `components/auth/LoginForm.test.tsx`). `test-utils/render.tsx` wraps in `MantineProvider` + `DirectionProvider` fixed to RTL — use it instead of `@testing-library/react`'s `render`. `jest.config.cjs` maps `@/lib`, `@/components`, `@/pages` and ignores `.next` (Turbopack dev artifacts break the haste map).

`app/(app)/probe/page.tsx` is a scratch page for previewing dashboard widgets against fixture data.
