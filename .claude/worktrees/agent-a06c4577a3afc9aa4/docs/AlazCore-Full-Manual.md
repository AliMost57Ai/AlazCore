# راهنمای جامع سامانه فروشگاه آنلاین آلاز (AlazCore OnlineShop)

سند مرجع کامل امکانات، منوها، صفحه‌ها، گزینه‌ها و رفتار سامانه — نوشته‌شده برای آموزش هوش مصنوعی، مستندسازی فنی و تحویل به تیم پشتیبانی.

نسخه سند: ۱٫۰ — شاخهٔ کد: `TicketingSys` — تاریخ: ۱۴۰۵/۰۷/۰۷ (۲۰۲۶-۰۹-۲۹)

---

## دربارهٔ این سند

این سند تمام سامانه را توصیف می‌کند: هر منو، هر صفحه، هر گزینه در هر صفحه، کاربرد هر گزینه، قواعد اعتبارسنجی، پیام‌های خطای فارسی، و مسیرهای فنی (API و مدل داده). ساختار آن طوری چیده شده که یک هوش مصنوعی بتواند با خواندنش به‌عنوان «دانش پایه»، به پرسش‌های کاربران دربارهٔ سامانه پاسخ دهد یا برای آن کد بنویسد.

اصول خواندن این سند:

- هر متن فارسی داخل گیومهٔ فارسی «...» **عیناً** همان رشته‌ای است که در رابط کاربری یا در پاسخ API دیده می‌شود. جایی که داخل گیومه آکولاد آمده (مثل «{n} سفارش»)، یعنی کد آن مقدار را جای‌گذاری می‌کند.
- هر نام لاتین داخل `code` یک شناسهٔ فنی است: نام فیلد در پایگاه داده، پارامتر API، یا مسیر فایل.
- مبالغ همه‌جا **عدد صحیح تومان** هستند.
- تاریخ‌ها همه‌جا **هجری شمسی (جلالی)** و به‌صورت رشتهٔ از پیش قالب‌بندی‌شده ذخیره می‌شوند.

# ۱. معرفی سامانه و معماری کلی

## ۱٫۱ سامانه چیست

یک فروشگاه اینترنتی فارسی و راست‌به‌چپ، ساخته‌شده روی Next.js 16 (App Router)، React 19، Mantine 8 و Prisma روی پایگاه‌دادهٔ SQLite. سامانه **دو بخش کاربری** دارد:

- **فروشگاه (Storefront)** — بخش عمومی برای مشتریان: صفحهٔ اصلی با قالب‌های قابل انتخاب، صفحهٔ کالا، سبد خرید، تسویه‌حساب، کیف پول، تیکت پشتیبانی.
- **پنل مدیریت (Admin Panel)** — بخش کارمندان: داشبورد، سفارش‌ها، مشتریان، محصولات، مالی، تیکت‌های پشتیبانی، تنظیمات.

به‌علاوه یک **ناحیهٔ حساب کاربری مشتری** زیر مسیر `/account` و یک **صفحهٔ عمومی پرداخت فاکتور** زیر مسیر `/pay/{token}` وجود دارد.

تمام متن‌های رابط کاربری، داده‌های نمونه و پیام‌های خطای API **فارسی** هستند. فونت رابط کاربری Vazirmatn است و جهت صفحه از کوکی `mnt_dir` خوانده می‌شود تا در اولین رنگ‌آمیزی درست باشد.

## ۱٫۲ نقشهٔ مسیرها

| بخش | مسیر | شرط دسترسی |
| --- | --- | --- |
| فروشگاه | `/` و `/shop/{slug}` | عمومی |
| صفحهٔ کالا | `/shop/{slug}` | عمومی (فقط کالاهای نمایان) |
| ورود و ثبت‌نام | `/login`، `/login-otp`، `/signup`، `/forgot` | عمومی |
| پرداخت با لینک | `/pay/{token}` | عمومی با توکن یکتا |
| ناحیهٔ مشتری | `/account`، `/account/orders`، `/account/wallet`، `/account/support`، `/account/password`، `/account/checkout` | نشست با نقش `customer` |
| پنل مدیریت | `/dashboard`، `/orders`، `/customers`، `/products`، `/coupons`، `/accounting`، `/payments`، `/price-updates`، `/price-history`، `/support`، `/users`، `/roles`، `/logs`، `/settings/...` | نشست کارمند + مجوز منو |
| API | `/api/**` | هر مسیر خودش احراز هویت می‌کند |

نکتهٔ مهم: مسیر `/shop` بدون پارامتر فقط یک ریدایرکت به `/` است. **فهرست کالاهای فروشگاه خودِ صفحهٔ اصلی است**، نه یک صفحهٔ جداگانه. همچنین **صفحهٔ `/cart` وجود ندارد** — سبد خرید یک کشوی کنارِ صفحه (Drawer) است که از هدر قالب باز می‌شود.

## ۱٫۳ معماری احراز هویت — سه لایه

دسترسی در این سامانه سه لایه دارد و هر لایه کار خودش را می‌کند:

۱. **لایهٔ پروکسی** (`proxy.ts`) — در Next.js 16 نام middleware به Proxy تغییر کرده و این فایل همان است. فقط ریدایرکت خوش‌بینانه انجام می‌دهد: امضای کوکی نشست را بررسی می‌کند و **هرگز** رکورد کاربر را از پایگاه‌داده نمی‌خواند. ترافیک بدون نشست را به `/login?next=...` می‌فرستد، کوکی دست‌کاری‌شده را پاک می‌کند، کاربر واردشده را از صفحه‌های ورود بیرون می‌کند، و دسترسی منویی کارمندان را چک می‌کند.
۲. **لایهٔ صفحه‌ها و چیدمان‌های سروری** (`lib/auth.ts`) — مرجع نهایی. توابع `requireSession()` و `canAccessMenu()` اینجا هستند. پروکسی مورد اعتماد نیست؛ هیچ صفحه‌ای صرفاً به این دلیل که کوکی وجود داشته رندر نمی‌شود.
۳. **لایهٔ مسیرهای API** (`lib/api-auth.ts`) — چون `matcher` پروکسی مسیر `api` را کنار می‌گذارد، **هر مسیر API خودش احراز هویت می‌کند**. سه تابع کمکی وجود دارد: `requireApiUser()` (هر کاربر واردشده)، `requireApiAdmin()` (فقط مدیر) و `requireApiMenu(href)` (مدیر یا کارمندی که آن منو را دارد). این توابع به‌جای ریدایرکت، پاسخ JSON با کد ۴۰۱ یا ۴۰۳ برمی‌گردانند.

الگوی مصرف در همهٔ مسیرها یکسان است:

```ts
const s = await requireApiUser();
if (s instanceof NextResponse) return s;
```

پیام‌های مشترک رد درخواست:

- ۴۰۱ — «برای این عملیات باید وارد شوید.»
- ۴۰۳ — «این عملیات فقط برای مدیران مجاز است.»
- ۴۰۳ منویی — «به این بخش دسترسی ندارید — با مدیر سایت تماس بگیرید.»

## ۱٫۴ نشست — توکن بدون حالت

نشست یک توکن **HMAC-SHA256 بدون حالت** است که در `lib/session.ts` ساخته می‌شود و فقط از Web Crypto و `btoa`/`atob` استفاده می‌کند؛ به همین دلیل همان کد هم در محیط Edge (پروکسی) و هم در Node اجرا می‌شود. **هیچ‌گاه نباید `node:crypto` به این فایل وارد شود**، وگرنه پروکسی از کار می‌افتد.

ساختار توکن: `<base64url(payload)>.<base64url(signature)>`

محتویات payload:

| فیلد | معنا |
| --- | --- |
| `sub` | شناسهٔ کاربر |
| `name` | نام نمایشی |
| `email` | ایمیل — برای مشتریانی که فقط موبایل دارند `null` است |
| `phone` | موبایل — برای کارمندان `null` است |
| `role` | یکی از `admin` / `member` / `customer` |
| `perms` | فهرست مسیرهای منویی؛ برای مدیر `['*']` |
| `exp` | زمان انقضا به ثانیهٔ یونیکس |

نام کوکی: `mnt_session` با پرچم‌های `httpOnly`، `sameSite: lax`، `secure` در محیط تولید، و `path: /`.

مدت اعتبار نشست:

| حالت | مدت | ثابت |
| --- | --- | --- |
| «مرا به خاطر بسپار» روشن، ثبت‌نام، و تازه‌سازی نشست | ۷ روز | `SESSION_MAX_AGE` |
| «مرا به خاطر بسپار» خاموش | ۸ ساعت | `SHORT_SESSION_MAX_AGE` |
| اعتبار کد یکبار مصرف ورود | ۱۲۰ ثانیه | `LOGIN_CODE_TTL_SECONDS` |
| کوکی مهمان پشتیبانی | ۳۰ روز | `SUPPORT_COOKIE_MAX_AGE` |

کلید امضا از متغیر محیطی `AUTH_SECRET` خوانده می‌شود و باید دست‌کم ۱۶ نویسه باشد؛ در محیط تولید مقدار کوتاه یا غایب باعث خطا می‌شود و فقط در توسعه یک مقدار جایگزین ناامن استفاده می‌گردد.

## ۱٫۵ ذخیره‌سازی رمز و کدها

- گذرواژه‌ها با **PBKDF2-SHA256**، صد هزار تکرار، کلید ۲۵۶ بیتی، نمک یکتای هر کاربر (UUID) و خروجی هگز حروف کوچک ذخیره می‌شوند. مقایسه با `timingSafeEqual` انجام می‌شود.
- برای اینکه زمان پاسخ، وجود یا نبود یک حساب را لو ندهد، تابع بررسی گذرواژه **همیشه** یک مشتق‌سازی کامل انجام می‌دهد — حتی وقتی حساب وجود ندارد.
- کد یکبار مصرف ورود و کد بازیابی گذرواژه به‌صورت `sha256(code:salt)` ذخیره می‌شوند، نه به‌صورت متن خام.
- گذرواژه‌ها **هرگز** در لاگ سیستمی نوشته نمی‌شوند.

## ۱٫۶ قواعد فنی که رفتار سامانه را تعیین می‌کنند

این قواعد در سراسر سامانه اثر دارند و دانستنشان برای درک رفتار صفحه‌ها لازم است:

- **بدون `Intl`** — قالب‌بندی عدد و تاریخ به‌صورت دستی پیاده شده است (`lib/format.ts`). دلیل: دادهٔ ICU مرورگر و Node می‌تواند متفاوت باشد و هر تفاوت به‌شکل خطای «عدم تطابق هیدریشن» در React ظاهر می‌شود. پیامد عملی: **همهٔ تاریخ‌ها از پیش قالب‌بندی‌شده ذخیره می‌شوند** — مثلاً `Order.date` یک رشتهٔ جلالی آماده است، نه یک تاریخ خام.
- **جدایی ماژول‌های سمت کلاینت از سمت سرور** — ثابت‌ها و منطق خالص در ماژول‌هایی زندگی می‌کنند که نه Prisma می‌شناسند و نه React، تا کامپوننت‌های کلاینتی بتوانند بدون کشیدن پایگاه‌داده به باندل از آن‌ها استفاده کنند. نمونه‌ها: `lib/order-status.ts` (امن) در برابر `lib/orders.ts` (Prisma)، و `lib/constants.ts` در برابر `lib/session.ts`.
- **SQLite ستون `Json` ندارد** — هر دادهٔ ساخت‌یافته به‌صورت **رشتهٔ JSON** ذخیره و در کد اعتبارسنجی می‌شود: `Product.props`، `Product.placements` و `Category.placements`، `Order.itemsJson`، `Role.permissions`، `ThemeConfig.config`، `MetaTag.content` و فهرست خبرنامه.
- **مسیر پایگاه‌داده ثابت است** — `file:../data/app.db` به‌صورت hardcode در `schema.prisma` نوشته شده تا CLI، seed و اجرای برنامه همیشه به یک فایل برسند و نیاز به تنظیم `.env` نباشد. این فایل gitignore شده و **دادهٔ زندهٔ کاربر** را نگه می‌دارد.
- **تغییر شِما فقط با `npm run db:push`** — پوشهٔ `prisma/migrations/` در این مخزن وجود ندارد و `prisma migrate` استفاده نمی‌شود.
- **پول همیشه از کیف پول** — درگاه پرداخت ابتدا کیف پول را شارژ می‌کند، سپس سفارش از کیف پول پرداخت می‌شود. این قاعده در سراسر سامانه یکسان است.
- **فاکتور فروش‌رفته هرگز بازنویسی نمی‌شود** — `Order.itemsJson` قیمت واحد هر قلم را در لحظهٔ ثبت سفارش کپی می‌کند؛ پس تغییر بعدی قیمت کالا روی فاکتورهای قبلی اثری ندارد.
# ۲. احراز هویت، نقش‌ها و سطوح دسترسی

## ۲٫۱ روش‌های ورود

سامانه سه روش ورود دارد (`lib/login-method.ts`):

| شناسهٔ فنی | برچسب فارسی | معنا |
| --- | --- | --- |
| `password` | «فقط گذرواژه» | شناسه + گذرواژه |
| `twostep` | «گذرواژه + کد یکبار مصرف (دو مرحله‌ای)» | اول گذرواژه، بعد کد پیامکی |
| `otp` | «فقط کد یکبار مصرف پیامکی» | فقط موبایل + کد پیامکی، بدون گذرواژه |

**قاعدهٔ تعیین روش ورود:** ابتدا سیاست سراسری سایت بررسی می‌شود (`AppSettings.loginPolicy`). اگر سیاست روی «همه دو مرحله‌ای» یا «همه رمز یکبار مصرف» باشد، **سیاست بر انتخاب کاربر مقدم است**. در غیر این صورت انتخاب خود کاربر (`User.loginMethod`) اعمال می‌شود که پیش‌فرضش «فقط گذرواژه» است.

نکتهٔ مهم: حساب‌های **کارمندی** (که با ایمیل وارد می‌شوند) همیشه با گذرواژه وارد می‌شوند؛ شاخهٔ ایمیل در کد ورود، سیاست را نادیده می‌گیرد.

## ۲٫۲ صفحهٔ ورود — `/login`

عنوان صفحه: «ورود به حساب» — زیرعنوان: «برای دیدن داشبورد، ابتدا وارد شوید.»

| فیلد / دکمه | برچسب | توضیح |
| --- | --- | --- |
| فیلد شناسه | «ایمیل یا شماره موبایل» | جای‌نگهدار: «you@example.com یا ۰۹۱۲۱۲۳۴۵۶۷» |
| فیلد گذرواژه | «گذرواژه» | جای‌نگهدار: «گذرواژه خود را وارد کنید» |
| چک‌باکس | «مرا به خاطر بسپار» | پیش‌فرض **روشن** — روشن یعنی نشست ۷ روزه، خاموش یعنی ۸ ساعته |
| دکمهٔ اصلی | «ورود به حساب» | |
| پیوند | «گذرواژه را فراموش کرده‌اید؟» | می‌رود به `/forgot` |
| پیوند | «ورود فقط با رمز یکبار مصرف (بدون گذرواژه)» | فرم را درجا به حالت رمز یکبار مصرف می‌برد |
| پیوند | «ثبت‌نام مشتری» | می‌رود به `/signup` |

اعتبارسنجی سمت کاربر: «ایمیل یا شماره موبایل (۰۹…) معتبر نیست.» و «گذرواژه باید حداقل ۸ نویسه باشد.»

پس از ورود: مشتری به فروشگاه (`/`) و کارمند به مقدار `?next=` می‌رود (اگر `next` نامعتبر باشد، به `/dashboard`). مقدار `next` فقط وقتی پذیرفته می‌شود که با `/` شروع شود و با `//` شروع نشود.

## ۲٫۳ صفحهٔ ورود با رمز یکبار مصرف — `/login-otp`

عنوان: «ورود با رمز یکبار مصرف» — زیرعنوان: «شماره موبایل خود را وارد کنید تا کد ورود برایتان پیامک شود.»

| فیلد | برچسب | توضیح |
| --- | --- | --- |
| شماره موبایل | «شماره موبایل» | توضیح: «شماره‌ای که با آن ثبت‌نام کرده‌اید — کد ورود به همین شماره پیامک می‌شود.» |
| دکمه | «دریافت کد ورود» | |

پیام‌های خطا: «ارسال کد ناموفق بود. لطفاً دوباره تلاش کنید.» و «برای این حساب، ورود با گذرواژه لازم است.» و «حسابی با این شماره موبایل یافت نشد.»

## ۲٫۴ مرحلهٔ کد یکبار مصرف (مشترک میان همهٔ جریان‌ها)

کامپوننت `OtpCodeStep` میان ورود دو مرحله‌ای، ورود با رمز یکبار مصرف و بازیابی گذرواژه مشترک است.

| عنصر | متن |
| --- | --- |
| راهنما | «کد ۶ رقمی ارسال‌شده به <شماره> را وارد کنید.» |
| شمارش معکوس | «زمان باقی‌مانده: mm:ss» با ارقام فارسی |
| فیلد کد | برچسب «کد یکبار مصرف»، توضیح «کد ۶ رقمی ارسال‌شده به موبایل شما»، جای‌نگهدار «------»، حداکثر ۶ نویسه |
| دکمهٔ تأیید | «تأیید و ورود» |
| دکمهٔ بازگشت | «بازگشت و اصلاح اطلاعات» — در فرم ورود با رمز یکبار مصرف: «بازگشت و اصلاح شماره» |
| پیام انقضا | «مهلت وارد کردن کد به پایان رسید — بازگشت بزنید و دوباره کد دریافت کنید.» |
| پیام توسعه | «کد آزمایشی (ارسال پیامک پیکربندی نشده): <کد>» — فقط وقتی ارسال پیامک تنظیم نشده باشد |
| خطا | «کد وارد شده نادرست است یا منقضی شده است.» |

کد یکبار مصرف **تک‌مصرف** است: پس از هر تلاش (موفق یا ناموفق) حالت انتظار پاک می‌شود. کد و توکن هر دو با نمک هش می‌شوند و با مقایسهٔ زمان‌ثابت بررسی می‌گردند.

## ۲٫۵ ثبت‌نام — `/signup`

عنوان: «ثبت‌نام مشتری» — زیرعنوان: «با شماره موبایل و یک گذرواژه حساب خود را بسازید.»

| فیلد | برچسب | توضیح |

## ۲٫۶ بازیابی گذرواژه — `/forgot`

دو مرحله دارد:

**مرحلهٔ ۱** — فیلد «شماره موبایل حساب» با توضیح «کد بازیابی برای این شماره ارسال می‌شود.» و دکمهٔ «دریافت کد بازیابی». خطاها: «شماره موبایل باید با ۰۹ شروع شود و دقیقاً ۱۱ رقم باشد.» و «حسابی با این شماره موبایل یافت نشد.» کد بازیابی ۱۵ دقیقه اعتبار دارد.

**مرحلهٔ ۲** — راهنما: «کد ۶ رقمی ارسال‌شده به <شماره> را وارد کنید.» فیلدها: «کد بازیابی» (جای‌نگهدار «۱۲۳۴۵۶»)، «گذرواژه جدید»، «تکرار گذرواژه جدید». دکمه: «تغییر گذرواژه». پیوندهای «شماره اشتباه بود؟» و «تغییر شماره». خطا: «کد نامعتبر یا منقضی شده است. دوباره درخواست کد بدهید.» موفقیت: «گذرواژه تغییر کرد» / «اکنون می‌توانید با گذرواژه جدید وارد شوید.»

## ۲٫۷ خروج از حساب

فقط با درخواست **POST** به `/api/auth/logout` انجام می‌شود. دلیل: اگر خروج با GET ممکن بود، هر تصویر جاسازی‌شده یا پیش‌بارگذاری مرورگر می‌توانست کاربر را خارج کند. در پاسخ، کوکی با `maxAge: 0` بازنویسی می‌شود.

## ۲٫۸ نقش‌ها

نقش کاربر در فیلد `User.role` به‌صورت **نام ماشینی** ذخیره می‌شود. سه نقش ساختهٔ خود برنامه هستند و کد به آن‌ها ارجاع می‌دهد:

| نام ماشینی | عنوان | دسترسی مدیر | منوها |
| --- | --- | --- | --- |
| `admin` | «مدیر کل» | بله | دسترسی کامل |
| `member` | «کارمند» | خیر | `/orders`، `/customers`، `/products`، `/settings/categories` |
| `customer` | «مشتری» | خیر | — (ناحیهٔ حساب کاربری) |
| `support` | «پشتیبان سایت» | خیر | `/support`، `/customers/file` |
| `finance_accountant` | «کارمند حسابداری» | خیر | `/accounting`، `/payments` |
| `finance_officer` | «کارمند مالی» | خیر | `/coupons`، `/price-updates` |
| `finance_manager` | «مدیر مالی» | خیر | `/coupons`، `/accounting`، `/payments`، `/price-updates` |

هفت نقش بالا در seed ساخته می‌شوند، ولی نقش‌های غیرساخته هم قابل تعریف‌اند: مدیر می‌تواند در صفحهٔ «نقش‌ها» نقش تازه با هر ترکیبی از منوها بسازد. نقش دارای پرچم «دسترسی مدیر» به همهٔ بخش‌ها می‌رسد و نیازی به انتخاب منو ندارد.

**تفکیک دو مفهوم که نباید اشتباه شوند:**

- `canAccessMenu(session, href)` پاسخ می‌دهد: «آیا این شخص اجازه دارد این کار را انجام دهد؟»
- `hasAdminAccess(session)` پاسخ می‌دهد: «آیا این شخص صاحب فروشگاه است؟» — یعنی `effectivePermissions(session).includes('*')`.

داشبورد، نمودارهای فروش، کاشی‌های درآمد و فهرست سفارش همهٔ مشتریان به پرسش دوم تعلق دارند. بنابراین کارمندی که دو سه منو دارد، صفحه‌های خودش را می‌گیرد ولی شماره‌های صاحب فروشگاه را نمی‌بیند.

### فهرست‌های ویژه

**`ADMIN_ONLY_HREFS`** — صفحه‌هایی که به غیرمدیر **داده نمی‌شوند**: `/users`، `/roles`، `/logs`، `/settings/payment`، `/settings/bnpl`، `/settings/sms`، `/settings/sms-templates`، `/settings/shahkar`، `/settings/security`، `/settings/shipping`، `/settings/support`.

**`ALWAYS_VISIBLE_HREFS`** — صفحه‌هایی که هر کارمند واردشده می‌تواند باز کند، مستقل از فهرست مجوزها: `/dashboard` و `/settings`.

**`ADMIN_ONLY_ROW_HREFS`** — ردیف‌هایی که **فقط در نوار کناری** به غیرمدیر نشان داده نمی‌شوند: `/dashboard`. این نکته ظریف است و دلیل دارد: `/dashboard` هم مقصد پیش‌فرض فرم ورود است و هم مقصد ریدایرکت حدود پانزده صفحهٔ محافظت‌شده. اگر خودِ صفحه به روی غیرمدیر بسته می‌شد، آن ریدایرکت‌ها به حلقهٔ بی‌پایان تبدیل می‌شدند. پس **صفحه باز می‌ماند ولی آنچه می‌کشد محدود می‌شود**؛ و این ثابت فقط نوار کناری را کنترل می‌کند، نه نگهبان‌ها را.

**`TOKEN_ONLY_HREFS`** — مجوزهایی که «توکن توانایی» هستند و صفحه‌ای پشتشان نیست: `/customers/file`. هرگز نباید به‌شکل پیوند رندر شوند.

**`ALTERNATE_GRANTS`** — صفحه‌هایی که بیش از یک مجوز بازشان می‌کند:

```ts
[{ prefix: '/customers/', anyOf: ['/customers', '/customers/file'] }]
```

یعنی پروندهٔ یک مشتری (`/customers/{id}`) هم با مجوز «مشتریان» باز می‌شود و هم با مجوز «مشاهدهٔ پروندهٔ مشتری» — ولی خودِ فهرست مشتریان (`/customers`) دست‌نخورده باقی می‌ماند و فقط با مجوز «مشتریان» باز می‌شود. این دقیقاً برای نقش «پشتیبان سایت» طراحی شده که باید پروندهٔ مشتری را ببیند ولی نه فهرست کامل مشتریان را.

### مجوزها یک «عکس لحظه‌ای» هستند

فهرست `perms` **در لحظهٔ ورود داخل توکن امضا می‌شود**. چون توکن بدون حالت است، **تغییر نقش یا مجوز تا زمانی که کاربر دوباره وارد نشود اثر نمی‌کند.** خودِ لاگ سیستمی هم این را تصریح می‌کند: «کاربران این نقش: <n> (اعمال از ورود بعدی)».

مدیران از این قاعده مستثنا هستند، ولی نه با ریختن `['*']` داخل توکن؛ بلکه تابع `effectivePermissions()` وقتی `role === 'admin'` باشد مقدار `['*']` برمی‌گرداند.

## ۲٫۱۰ رفتار داشبورد برای کاربران غیرمدیر

صفحهٔ `/dashboard` برای **همه** باز است (۲۰۰ می‌دهد) ولی محتوایش دو حالت دارد:

- **مدیر:** نمودارها، کاشی‌های آماری، نمودار درآمد، ترکیب دسته‌بندی، و جدول پنج سفارش آخر. فیلتر «بازه زمانی» با گزینه‌های «۳۰ روز گذشته»، «۹۰ روز گذشته»، «یک سال گذشته» (پیش‌فرض: یک سال).
- **غیرمدیر:** کارت «دسترسی‌های شما» — سلام با نام کوچک، توضیح «نمودارها و آمار فروش داشبورد فقط برای مدیران نمایش داده می‌شود. صفحه‌هایی که برای شما تعیین شده از اینجا در دسترس است.»، و شبکهٔ پیوندهایی به منوهای واگذارشده. اگر هیچ منویی نداشته باشد: هشدار «هنوز دسترسی‌ای برای شما ثبت نشده است» با متن «برای تعیین دسترسی‌های خود با مدیر سیستم تماس بگیرید.» در پایین همیشه پیوند «حساب کاربری و تنظیمات نمایش» به `/settings`.

نکتهٔ پیاده‌سازی مهم: این تصمیم **پیش از اجرای کوئری‌ها** گرفته می‌شود. یعنی برای غیرمدیر، آمار فروشگاه حتی از پایگاه‌داده خوانده هم نمی‌شود — نه اینکه خوانده و پنهان شود.

| وضعیت فعلی | دکمه‌های موجود |

پنجره‌های تأیید:

- **«شروع بسته‌بندی»** — «سفارش <شناسه> به حالت بسته‌بندی برود؟ وضعیت آن برای مشتری به «در حال بسته‌بندی» تغییر می‌کند.» دکمه‌ها: «انصراف» / «ثبت».
- **«لغو سفارش»** — «سفارش <شناسه> لغو شود؟ این عمل قابل بازگشت نیست و مشتری آن را در تب «لغو شده» می‌بیند.» دکمه‌ها: «انصراف» / «لغو سفارش».
- **فرم ثبت ارسال** (بازشو، داخل ردیف) — فیلد «کد رهگیری» و انتخابگر «تاریخ تخمینی تحویل». گزینه‌های تاریخ: ده روز آینده به‌صورت تاریخ کامل جلالی، با پیش‌فرض **سه روز بعد از امروز** (چون تیپاکس حداقل سه روز تحویل تضمین می‌کند).

### قواعد سرور عملیات سفارش

| عملیات | قاعده |
| --- | --- |
| بسته‌بندی | فقط از «پرداخت شده» یا «در حال بسته‌بندی» — وگرنه «فقط سفارش‌های پرداخت‌شده قابل بسته‌بندی هستند.» |
| ثبت ارسال | فقط از «در حال بسته‌بندی» — وگرنه «ابتدا سفارش را به حالت بسته‌بندی ببرید.» کد رهگیری الزامی و حداکثر ۱۰۰ نویسه: «کد رهگیری مرسوله را وارد کنید (حداکثر ۱۰۰ نویسه).» تاریخ تحویل الزامی: «تاریخ تخمینی تحویل به مشتری را انتخاب کنید.» |
| اطلاع‌رسانی پیامک | فقط از «ارسال شده» — وگرنه «برای اطلاع‌رسانی، سفارش باید در حالت ارسال شده باشد.» |
| تحویل شد | فقط از «ارسال شده» — وگرنه «فقط سفارش‌های ارسال‌شده قابل تحویل هستند.» |
| لغو | برای سفارش «تحویل شده» یا «لغو شده»: «این سفارش در وضعیت نهایی است و قابل لغو نیست.» |

**قاعدهٔ بازگشت وجه در لغو سفارش:** اگر سفارش پرداخت‌نشده باشد، فقط لغو می‌شود و پیام «سفارش پرداخت‌نشده بود؛ مبلغی برگشت نخورد.» می‌آید. اگر پرداخت‌شده باشد، مبلغ `amount − discountAmount + shippingCost` (با کف صفر) به کیف پول مشتری برمی‌گردد با شرح «لغو سفارش <شناسه>»، و استفاده از کد تخفیف آن سفارش هم آزاد می‌شود. **موجودی انبار برنمی‌گردد** — چون ممکن است کالا بسته‌بندی یا ارسال شده باشد.

هر تغییر واقعی وضعیت در لاگ سیستمی ثبت می‌شود: «وضعیت سفارش <شناسه> از «<از>» به «<به>» تغییر کرد.» کلیک تکراری روی همان وضعیت چیزی نمی‌نویسد.

### واژه‌نامهٔ وضعیت سفارش

| کلید | برچسب فارسی | رنگ | آیکون |
| --- | --- | --- | --- |
| `paid` | «پرداخت شده» | سبز | تیک |
| `pending` | «در انتظار پرداخت» | زرد | ساعت |
| `boxing` | «در حال بسته‌بندی» | بنفش | بسته |
| `posted` | «ارسال شده» | آبی | کامیون |
| `shipped` | «ارسال شده» | آبی | کامیون |
| `delivered` | «تحویل شده» | فیروزه‌ای | تیک دایره‌ای |
| `cancelled` | «لغو شده» | قرمز | هشدار |

زیروضعیت‌های تحویل (روی کارت سفارش مشتری): `delivered` «تحویل داده شد» · `stage2` «مرحله ۲» · `cancelled` «لغو شده» · `seller` «نزد فروشنده».

رویداد جاری: `pending` «در انتظار پرداخت» · `paid` «پرداخت تأیید شد» · `boxing` «در حال بسته‌بندی» · `posted`/`shipped` «تحویل به تیپاکس» · `delivered` «تحویل به مشتری».

گام بعدی: `pending` «پرداخت آنلاین» · `paid` «بسته‌بندی توسط فروشگاه» · `boxing` «تحویل به تیپاکس» · `posted`/`shipped` «دریافت در تیپاکس».

### خروجی اکسل سفارش‌ها

فایل `.xlsx` با نام شیت «سفارش‌ها»، راست‌به‌چپ، سرصفحهٔ چسبان و پررنگ. ستون‌ها: «شناسه سفارش»، «مشتری»، «موبایل»، «تاریخ»، «مبلغ (تومان)»، «وضعیت»، «کد رهگیری». نام فایل: `orders-YYYY-MM-DD.xlsx`.

## ۳٫۴ مشتریان — `/customers`

عنوان: «مشتریان» — توضیح: «<n> مشتری ثبت‌نام‌شده در فروشگاه».

نوار فیلتر: جستجوی «جستجوی نام مشتری یا موبایل…» و دکمهٔ «جستجو». جستجو روی نام یا موبایل مشتریان (`role = customer`) و به‌ترتیب تازه‌ترین عضویت.

فهرست، شبکه‌ای از کارت‌های مشتری است. هر کارت نشان می‌دهد: تصویر حرف‌اول نام (یا «؟»)، نام، نشان قرمز «مسدود» در صورت مسدود بودن، نشان سطح مشتری (طلایی/نقره‌ای/برنزی)، شمارهٔ موبایل، و چهار آمار: «سفارش‌ها» (تعداد سفارش‌های لغونشده)، «مجموع خرید»، «کیف پول»، «عضویت» (تاریخ جلالی).

**آستانه‌های سطح مشتری:** طلایی از ۱۰۰٬۰۰۰٬۰۰۰ تومان، نقره‌ای از ۵۰٬۰۰۰٬۰۰۰ تومان، وگرنه برنزی.

دکمه‌های هر کارت:

| دکمه | کار |
| --- | --- |
| «سفارش‌ها و سبد» | پنجرهٔ جزئیات |
| «کیف پول» | پنجرهٔ تنظیم موجودی |
| «تماس» | پیوند `tel:` |
| «مشاهدهٔ پروندهٔ مشتری» | می‌رود به `/customers/{id}` |
| «مسدود کردن مشتری» / «رفع مسدودی» | تغییر وضعیت حساب |

حالت‌های خالی: با جستجو «مشتری‌ای با این مشخصات یافت نشد.» و بدون جستجو «هنوز مشتری‌ای در فروشگاه ثبت‌نام نکرده است. با اولین ثبت‌نام مشتری در فروشگاه اینجا نمایش داده می‌شود.»

### پنجرهٔ «سفارش‌ها و سبد <نام>»

- بخش «سبد خرید فعال (سفارش پرداخت‌نشده)» — شناسه، مبلغ و اقلام «<نام> × <تعداد>»، یا «این مشتری سفارش پرداخت‌نشده‌ای ندارد.»
- بخش «سفارش‌های اخیر» — حداکثر ۵ سفارش آخر با نشان وضعیت، شناسه، تاریخ و مبلغ، یا «هنوز سفارشی ثبت نکرده است.»
- دکمهٔ پایین: «مشاهدهٔ پروندهٔ کامل مشتری».

### پنجرهٔ «کیف پول <نام>»

| عنصر | برچسب | توضیح |
| --- | --- | --- |
| موجودی | «موجودی فعلی» | فقط‌خواندنی |
| نوع تغییر | «افزایش موجودی» / «کاهش موجودی» | |
| مبلغ | «مبلغ (تومان)» | جای‌نگهدار «مثلاً ۵۰۰۰۰۰» |
| دلیل | «دلیل» | جای‌نگهدار «مثلاً جبران کالای معیوب» |
| دکمه | «ثبت تغییر» | |

اعتبارسنجی: «مبلغ باید حداقل ۱۰۰ تومان باشد.» و «دلیل تغییر موجودی را بنویسید (حداقل ۳ نویسه).» قواعد سرور: مبلغ عدد صحیح تا دو میلیارد («مبلغ باید عددی مثبت باشد.»)، دلیل حداقل ۳ نویسه («دلیل تعدیل را وارد کنید (حداقل ۳ نویسه).»)، و در کسر بیش از موجودی: «موجودی کیف پول مشتری برای این کسر کافی نیست.» هر تعدیل با نوع `admin_adjust` و شرح «<دلیل> — توسط <نام کارمند>» در دفتر کیف پول ثبت می‌شود.

### پنجرهٔ مسدودسازی

عنوان «مسدود کردن مشتری» یا «رفع مسدودی». متن: «<نام> تا زمانی که مسدود است نمی‌تواند وارد حسابش شود.» یا «<نام> پس از رفع مسدودی می‌تواند دوباره وارد حسابش شود.» دکمه‌ها: «انصراف» / «مسدود کن» (یا «رفع مسدودی»).

## ۳٫۵ پروندهٔ مشتری — `/customers/{id}`

دسترسی: با مجوز «مشتریان» **یا** مجوز «مشاهدهٔ پروندهٔ مشتری». اگر شناسه نامعتبر باشد یا حساب متعلق به یک کارمند باشد، صفحه ۴۰۴ می‌شود.

عنوان: «پروندهٔ <نام>» — توضیح: «<n> سفارش · مجموع خرید <مبلغ> · عضویت از <تاریخ>».

این صفحه کاملاً **فقط‌خواندنی** است؛ هر تغییر جای خودش را دارد. بخش‌ها به ترتیب:

۱. **کارت هویت** — نام، نشان «مسدود» در صورت لزوم، نشان سطح، موبایل، ایمیل (اختیاری)، «کد ملی: <کد>` در صورت وجود؛ و چهار آمار «سفارش‌ها» / «مجموع خرید» / «کیف پول» / «عضویت».
۲. **«سفارش‌ها و سبد خرید»** — سبد فعال یا «سفارش پرداخت‌نشدهٔ فعالی ندارد.» ستون‌ها: «سفارش» (شناسه + تاریخ)، «اقلام» («<نام> × <تعداد>»)، «مبلغ»، «وضعیت» (با نشان آبی «سبد فعال» برای سفارش در انتظار پرداخت)، «کد رهگیری». خالی: «این مشتری هنوز سفارشی ثبت نکرده است.»
۳. **«کیف پول»** — موجودی فعلی. ستون‌ها: «تاریخ»، «شرح»، «مبلغ» (با علامت مثبت/منفی، سبز برای افزایش). خالی: «تراکنشی در کیف پول این مشتری ثبت نشده است.»
۴. **«تراکنش‌های درگاه»** — «هر تلاش پرداخت، موفق یا ناموفق.» ستون‌ها: «تاریخ»، «نوع»، «مبلغ»، «سفارش»، «کد پیگیری»، «وضعیت». خالی: «پرداخت آنلاینی برای این مشتری ثبت نشده است.»
۵. **«تیکت‌های پشتیبانی»** — «<n> گفتگو». ستون‌ها: «تیکت»، «موضوع»، «وضعیت» (با نشان قرمز «خوانده‌نشده» در صورت لزوم)، «آخرین پیام»، و ستون عملیات با پیوند «مشاهده گفتگو» — **فقط اگر مجوز `/support` داشته باشید**، وگرنه «—». خالی: «این مشتری تیکتی ثبت نکرده است.»
۶. **«کدهای تخفیف مصرف‌شده»** — کد (مونواسپیس)، مقدار («٪۱۰» یا «۵۰٬۰۰۰ تومان») و تاریخ. خالی: «این مشتری از هیچ کد تخفیفی استفاده نکرده است.»
۷. **«آدرس‌ها»** — «<n> آدرس ثبت‌شده». هر آدرس: عنوان، کدپستی، «<نام گیرنده> — <موبایل گیرنده>» و متن نشانی. خالی: «آدرسی برای این مشتری ثبت نشده است.»

فهرست دفتر کیف پول و تراکنش‌های درگاه در این صفحه به ۵۰ ردیف آخر محدود است.

## ۳٫۶ تیکت‌های پشتیبانی — `/support`

عنوان: «تیکت‌های پشتیبانی» — توضیح پویا: اگر تیکت خوانده‌نشده باشد «<n> تیکت در انتظار پاسخ شماست.» وگرنه «همهٔ تیکت‌ها پاسخ داده شده‌اند.»

این صفحه **خودکار تازه می‌شود** — هر ۲۰ ثانیه و همچنین به‌محض بازگشت به تب.

### فیلترها

| عنصر | برچسب | توضیح |
| --- | --- | --- |
| جستجو | «جستجوی شماره تیکت، موضوع، نام یا موبایل…» | روی شناسهٔ تیکت، موضوع، نام و موبایل مهمان یا کاربر |
| کنترل بخش‌بندی وضعیت | «همه» / «در انتظار پاسخ» / «پاسخ داده شده» / «بسته شده» | |
| کلید | «فقط خوانده‌نشده‌ها» | با `?unread=1` در نشانی — قابل نشانک‌گذاری |
| دکمه | «جستجو» | |

### ستون‌های جدول

«شماره» (شناسهٔ `TK-xxxxx`) · «درخواست‌کننده» (نام + نشان «مهمان» در صورت مهمان بودن، موبایل زیر آن) · «موضوع» · «وضعیت» · «آخرین پیام» (با پیشوند «پشتیبان: » اگر آخرین پیام از کارمند باشد، و تاریخ زیر آن) · ستون عملیات با نشان قرمز «خوانده‌نشده» در صورت لزوم و پیوند «مشاهده گفتگو».

صفحه‌بندی: هر صفحه ۲۰ تیکت، با دکمه‌های «صفحه قبل» / «صفحه <n>» / «صفحه بعد». خالی: «تیکتی با این فیلترها یافت نشد.»

### وضعیت‌های تیکت

| کلید | برچسب | رنگ |
| --- | --- | --- |
| `open` | «در انتظار پاسخ» | نارنجی |
| `answered` | «پاسخ داده شده» | فیروزه‌ای |
| `closed` | «بسته شده» | خاکستری |

**خوانده‌نشده محاسبه نمی‌شود، استنتاج می‌شود:** یک تیکت برای پشتیبان خوانده‌نشده است اگر تازه‌ترین پیام از سمت درخواست‌کننده باشد و از `staffReadAt` جدیدتر باشد. تیکتی که هرگز باز نشده، خوانده‌نشده حساب می‌شود. سمت مشتری دقیقاً آینهٔ همین قاعده است.

**اولویت تیکت وجود ندارد.** نه فیلد اولویت، نه شدت، و نه «پاسخ آماده» در این سامانه تعریف نشده است.

### صفحهٔ یک تیکت — `/support/{id}`

عنوان: «گفتگوی پشتیبانی» — باز کردن این صفحه، تیکت را برای پشتیبان خوانده‌شده می‌کند.

چیدمان دو ستونی: گفتگو (۸ واحد) و پنل زمینه (۴ واحد). پنل زمینه هر ۶۰ ثانیه و خودِ گفتگو هر ۱۰ ثانیه تازه می‌شود.

**کامپوننت گفتگو:**

- سرصفحه: موضوع، زیرنویس «تیکت <شناسه> — <نام درخواست‌کننده>» و برای مهمان «(مهمان)»، نشان وضعیت، و دکمهٔ «بستن تیکت» یا «بازکردن تیکت».
- حباب پیام‌ها: پیام‌های پشتیبان راست‌چین با پس‌زمینهٔ فیروزه‌ای روشن و زیرنویس «پشتیبان — <نام> — <تاریخ>»؛ پیام‌های درخواست‌کننده چپ‌چین با زیرنویس «<نام> — <تاریخ>».
- کادر پاسخ: جای‌نگهدار «پاسخ خود را بنویسید…»، حداکثر ۲۰۰۰ نویسه، و دکمهٔ ارسال با برچسب دسترس‌پذیری «ارسال پاسخ». در تیکت بسته به‌جای آن هشدار «این تیکت بسته است — برای پاسخ‌دادن، ابتدا آن را باز کنید.» می‌آید.
- پیام‌ها: موفقیت بستن/بازکردن «تیکت بسته شد.» / «تیکت باز شد.» — خطاها «ارسال پاسخ ناموفق بود.» / «تغییر وضعیت تیکت ناموفق بود.» / «ارتباط با سرور برقرار نشد.»

**پنل زمینه (فقط‌خواندنی، عمداً):** پاسخ‌دادن به تیکت هرگز نباید پول جابه‌جا کند.

- **تیکت مهمان:** کارت «درخواست‌کننده» با نام مهمان (یا «کاربر مهمان»)، نشان «مهمان»، موبایل در صورت وجود، و توضیح «این کاربر مهمان است و حساب کاربری ندارد؛ بنابراین سفارش و کیف پولی برای نمایش وجود ندارد. برای پیگیری، از همین گفتگو یا شمارهٔ بالا استفاده کنید.»
- **تیکت دارای حساب:** سه کارت:
  ۱. «مشتری» — نام، موبایل، ایمیل، نشان‌های «<n> سفارش» و «<n> تیکت باز»؛ سپس پیوند «مشاهدهٔ پروندهٔ مشتری» یا در نبود مجوز «برای دیدن پروندهٔ کامل مشتری، دسترسی «مشاهدهٔ پروندهٔ مشتری» لازم است.»
  ۲. «آخرین سفارش» — شناسه، وضعیت، مبلغ، تاریخ، کد رهگیری؛ یا «این مشتری هنوز سفارشی ثبت نکرده است.»
  ۳. «وضعیت کیف پول» — «موجودی» و تا پنج تراکنش آخر؛ یا «تراکنشی در کیف پول این مشتری ثبت نشده است.» یادداشت پایانی: «این پنل فقط خواندنی است؛ برای تغییر موجودی از صفحهٔ مشتریان استفاده کنید.»

**قواعد سرور تیکت:**

- تغییر وضعیت فقط برای پشتیبان است: «تغییر وضعیت تیکت فقط برای پشتیبان است.» وضعیت نامعتبر: «وضعیت تیکت نامعتبر است.»
- پیام در تیکت بسته: «این تیکت بسته شده است — برای ادامهٔ گفتگو آن را باز کنید.»

- کارمندان نمی‌توانند از مسیر فروشگاهی تیکت بسازند: «کارمندان از این مسیر تیکت ثبت نمی‌کنند.»

### قواعد اعتبارسنجی کد تخفیف — به ترتیب بررسی

۱. کد خالی → «کد تخفیف را وارد کنید.»
۲. کد ناشناخته یا غیرفعال → «کد تخفیف نامعتبر است.»
۳. تاریخ انقضای گذشته → «این کد تخفیف منقضی شده است.»
۴. تکمیل ظرفیت → «ظرفیت استفاده از این کد تخفیف تکمیل شده است.»
۵. کد اختصاصی که متعلق به حساب دیگری است → «این کد تخفیف برای حساب شما فعال نیست.»
۶. استفادهٔ قبلی همین مشتری → «شما قبلاً از این کد تخفیف استفاده کرده‌اید.» (ردیف مصرف فقط پس از پرداخت موفق ساخته می‌شود، پس تلاش پرداخت‌نشده مانع تلاش دوباره نیست)
۷. کمتر از حداقل مبلغ خرید → «حداقل مبلغ خرید برای این کد تخفیف <مبلغ> تومان است.»
۸. شرط خرید کالای خاص → نیاز به ورود («برای استفاده از این کد تخفیف باید وارد حساب خود شوید.») و داشتن سفارش **پرداخت‌شده** حاوی آن کالا در بازهٔ تعیین‌شده، وگرنه «این کد تخفیف فقط برای خریداران محصول «<نام>» در بازه تعیین‌شده است.»
۹. شرط مجموع خرید قبلی → «این کد تخفیف فقط برای مشتریانی است که مجموع خریدهای قبلی‌شان <عملگر> <مبلغ> تومان باشد. مجموع خرید شما: <مبلغ> تومان.»
۱۰. **پایهٔ تخفیف:** کل سفارش، محدودشده به خطوط محصول منتسب (خطای «این کد تخفیف فقط برای محصول «<نام>» است.» وقتی پایه صفر شود) و/یا خطوط دستهٔ منتسب به‌همراه زیردسته‌ها («این کد تخفیف فقط برای کالاهای دسته «<نام>» است.»). اگر هر دو شرط باشند، شرط دسته بر محصول مقدم است.
۱۱. **مقدار:** درصدی → کف `پایه × مقدار ÷ ۱۰۰`؛ مبلغی → کمینهٔ مقدار و پایه (تخفیف مبلغی هرگز از پایهٔ خود بیشتر نمی‌شود).

## ۳٫۱۰ حسابداری — `/accounting`

عنوان: «حسابداری» — توضیح: «<n> سفارش — جمع پرداخت‌ها <مبلغ> تومان». این صفحه **کاملاً فقط‌خواندنی** است و هیچ عملیات یا API ندارد.

نوار فیلتر: «جستجوی شناسه سفارش، نام مشتری یا موبایل…» و دکمهٔ «جستجو». فقط سفارش‌هایی که به یک حساب کاربری وصل‌اند در دامنه‌اند، تازه‌ترین اول، حداکثر ۲۰۰ ردیف.

### ستون‌های جدول

«سفارش» (شناسه + تاریخ) · «مشتری» (نام + موبایل) · «قیمت اصلی» · «تخفیف فروشگاه» (نارنجی، یا «—») · «کد تخفیف» (کد + مبلغ، یا «—») · «قابل پرداخت» · «پرداخت آنلاین» (یا «—») · «از کیف پول» (یا «—») · «وضعیت» (نشان وضعیت، و در صورت بازگشت وجه یک خط قرمز «بازگشت <مبلغ>»).

تعریف محاسباتی ستون‌ها:

- `productDiscount = base − amount` که `base = max(baseAmount, amount)` است (ردیف‌های قدیمی به‌نرمی تخریب می‌شوند).
- `payable = amount − discountAmount + shippingCost`
- `onlinePaid` = جمع تراکنش‌های **تأییدشدهٔ** «شارژ کیف پول» مرتبط با همان سفارش، و فقط وقتی سفارش تاریخ پرداخت داشته باشد.
- `walletPaid = max(payable − onlinePaid, 0)` و تنها در همان شرایط.
- `refunded = payable` وقتی سفارش لغو شده **و** پرداخت شده باشد.

حالت خالی: «سفارشی برای نمایش وجود ندارد.» و با فیلتر: «سفارشی با این مشخصات یافت نشد.»

## ۳٫۱۱ تراکنش‌های درگاه — `/payments`

عنوان: «تراکنش‌های درگاه» — توضیح: «<n> تلاش — <n> موفق».

جدول همهٔ تلاش‌های پرداخت آنلاین همهٔ مشتریان، تازه‌ترین اول، حداکثر ۲۰۰ ردیف. ستون‌ها: «تاریخ» · «مشتری» · «نوع» (نشان آبی) · «مبلغ» · «وضعیت» (زرد = در انتظار، سبز = موفق، قرمز = ناموفق) · «کد پیگیری» (یا «—») · «سفارش» (شناسه یا «—»). خالی: «تراکنش درگاه موجود نیست.» این صفحه فیلتر و عملیات ندارد.

### واژه‌نامهٔ پرداخت

انواع تلاش: `wallet_charge` «شارژ کیف پول» · `order_payment` «پرداخت سفارش». حالت‌ها: `pending` «در انتظار» · `verified` «موفق» · `failed` «ناموفق». هر مقدار ناشناخته «در انتظار» خوانده می‌شود.

انواع دفتر کیف پول: `charge` «شارژ کیف پول» · `order_payment` «پرداخت سفارش» · `refund` «بازگشت وجه» · `admin_adjust` «تعدیل توسط فروشگاه». مقدار ناشناخته «تعدیل توسط فروشگاه» خوانده می‌شود.

| هدف | «هدف تغییر» | «گروه کالا» یا «کالا» — تغییر این مقدار، هدف انتخاب‌شده را پاک می‌کند |
| هدف | انتخابگر | «یک گروه یا دسته انتخاب کنید» یا «یک کالا انتخاب کنید» |
| نوع تغییر | «نوع و مقدار تغییر» | «درصد» یا «عدد ثابت (تومان)» |
| مقدار | عدد | درصد: از ۱۰۰− تا ۱۰۰۰. ثابت: حداکثر یک میلیارد تومان |

راهنمای مقدار: «مقدار منفی = کاهش قیمت. قیمت‌ها هرگز از صفر کمتر نمی‌شوند.»

**پیش‌نمایش:** به‌محض انتخاب هدف و مقدار معتبر غیرصفر، جدولی نمایش داده می‌شود که با **همان تابع خالصی که سرور استفاده می‌کند** محاسبه شده — پس پیش‌نمایش دقیقاً همان چیزی است که اعمال می‌شود. ستون‌ها: «کالا»، «نوع» («—» برای قیمت خود محصول)، «قیمت فعلی»، «قیمت جدید». اگر تغییری لازم نباشد: «هیچ قیمتی با این تغییر جابه‌جا نمی‌شود.»

پنجرهٔ تأیید: «<n> قیمت در «<هدف>» با <تغییر> به‌روزرسانی شود؟ قیمت سفارش‌های قبلی تغییر نمی‌کند و این تغییر در تاریخچه ثبت می‌شود.» دکمه‌ها: «انصراف» / «ثبت».

**قواعد محاسبه:**

- دامنهٔ «گروه کالا» شامل خود دسته **و همهٔ زیردسته‌هایش** است (تا هر عمقی). دامنهٔ «کالا» شامل خود محصول و همهٔ نوع‌هایش است.
- «عدد ثابت» یعنی `قدیم + مقدار`. «درصد» یعنی `round(قدیم × (۱۰۰ + مقدار) ÷ ۱۰۰)`.
- هر دو حالت در **صفر تومان** متوقف می‌شوند؛ قیمت منفی ممکن نیست.
- **قاعدهٔ نوع‌ها:** نوعی که قیمت اختصاصی ندارد (`price === null`) قیمت محصول را **ارث می‌برد**، پس با محصول جابه‌جا می‌شود و **ردیف تاریخچه نمی‌گیرد**. فقط نوع‌هایی که قیمت مستقل دارند تغییر مستقل ثبت می‌کنند.
- **فاکتورهای فروش‌رفته هرگز دست نمی‌خورند** — چون `Order.itemsJson` قیمت لحظهٔ خرید را کپی کرده است.
- **دلیل متنی آزاد وجود ندارد.** زمینهٔ حسابرسی خودِ تغییر است: دامنه (گروه/دسته یا محصول)، نام هدف، نوع و مقدار تغییر، عامل و زمان — که به‌شکل «۱۰٪ افزایش» یا «۵۰٬۰۰۰ تومان کاهش» نمایش داده می‌شود.
- یک ردیف لاگ سیستمی هم نوشته می‌شود: «قیمت‌های «<هدف>» <تغییر> یافت (<n> مورد).» با جزئیات هدف، نوع تغییر، تعداد و بازهٔ قیمت جدید.

خطاها: «درخواست نامعتبر است.» / «نوع هدف باید گروه کالا یا کالا باشد.» / «هدف تغییر قیمت مشخص نشده است.» / «نوع تغییر باید عدد ثابت یا درصد باشد.» / «مقدار تغییر باید عدد باشد.» / «درصد تغییر باید بین ۱۰۰- و ۱۰۰۰ باشد.» / «هدف تغییر قیمت یافت نشد.» / «هیچ قیمتی با این تغییر جابه‌جا نمی‌شود.»

**نمایش ردیف‌ها:** تاریخچه در **دسته‌های عملیاتی (batch)** گروه‌بندی می‌شود، تازه‌ترین دسته اول. هر دسته با یک جداکنندهٔ وسط‌چین شروع می‌شود: «<تاریخ کامل جلالی> — <نام عامل> — «<نام هدف>» (<تغییر>)». سپس جدولی با ستون‌های «کالا»، «نوع» (نام نوع، یا «قیمت کالا» برای قیمت خود محصول)، «قیمت قبلی»، «قیمت جدید»، «تعداد تغییر» (درصد تغییر با یک رقم اعشار، یا «—» وقتی قیمت قبلی صفر بوده).

**صفحه‌بندی بر اساس دسته است، نه ردیف** — چون یک عملیات روی ۲۰۰ کالا نباید کل یک صفحه را بخورد. هر صفحه ۲۰ دسته.

## ۴٫۷ پشتیبانی — `/settings/support`

عنوان صفحه: «پشتیبانی» — توضیح: «فعال یا غیرفعال کردن گفتگوی پشتیبانی در فروشگاه و متن خوش‌آمد آن.»

این صفحه **سه کارت** دارد و هر کارت چند گزینه. فهرست کامل گزینه‌ها:

### نکتهٔ فنی دربارهٔ دو فیلد ثانیه‌ای

هر دو فیلد ثانیه («تأخیر نمایش آیکون» و «مدت نمایش پیام خوش‌آمد») تا رسیدن به API به‌صورت **رشته** حمل می‌شوند. دلیل: `FIELD_SPECS` در `lib/settings.ts` پنج نوع دارد و **نوع عددی ندارد**؛ پس عددها مثل بقیهٔ عددهای سامانه (نمونهٔ موجود: تعداد اقساط وایب) رشته ذخیره می‌شوند. اعتبارسنجی سمت سرور الگوی «حداکثر سه رقم» را می‌پذیرد و مقدار ناشناخته در سمت فروشگاه به پیش‌فرض برمی‌گردد (تابع `resolveSupportWidgetConfig()` هرگز استثنا پرتاب نمی‌کند).

## ۴٫۸ امنیت سامانه — `/settings/security`

عنوان: «امنیت سامانه» — توضیح: «سیاست ورود سایت — روش ورود مشتریان و اجباری‌کردن ورود دو مرحله‌ای یا رمز یکبار مصرف.» — آیکون سپر.

یک کارت با عنوان «سیاست ورود سایت» و یک `SegmentedControl` تمام‌عرض با چهار گزینه:

| مقدار | برچسب | معنا |
| --- | --- | --- |
| `''` | «انتخاب کاربر» | هر مشتری روش ورود خود را در پروفایلش انتخاب می‌کند |
| `password` | «همه فقط گذرواژه» | رفتار پیش‌فرض |
| `twostep` | «همه دو مرحله‌ای» | اجباری برای همه |
| `otp` | «همه رمز یکبار مصرف» | اجباری برای همه |

دو متن راهنما زیر آن: «در حالت «انتخاب کاربر» هر مشتری روش ورود خود را در پروفایلش (/account) برمی‌گزیند. حالت‌های «دو مرحله‌ای» و «رمز یکبار مصرف» برای همه اجباری می‌شوند و انتخاب کاربر غیرفعال می‌شود. (حالت «همه فقط گذرواژه» همان رفتار پیش‌فرض است.)» و «متن و الگوی پیامک کد ورود در صفحه «الگوهای پیامکی» تنظیم می‌شود.»

دکمه: «ذخیره سیاست ورود». موفقیت: «ذخیره شد» / «سیاست ورود سایت به‌روزرسانی شد.» — خطا: «ذخیره سیاست ورود ناموفق بود.»

**اثر جانبی مهم:** وقتی سیاست روی «دو مرحله‌ای» یا «رمز یکبار مصرف» باشد، در `/account` انتخاب روش ورود برای مشتری **قفل** می‌شود. حساب‌های کارمندی (ورود با ایمیل) همیشه با گذرواژه وارد می‌شوند و این سیاست شاملشان نمی‌شود.

### ردیف اعتبارنامه — رفتار مشترک

هر ردیف یک برچسب در بالا و یک گروه فیلد به‌هم‌چسبیده دارد. کنارش دو کلید می‌آید: کلید «فعال» و کلید «درگاه پیش‌فرض». فیلدهای رمز با دکمهٔ چشم قابل مشاهده‌اند. اگر درگاهی پیکربندی نشده باشد، یک نشان زرد «پیکربندی نشده» کنارش ظاهر می‌شود.

### کارت «اتصال به ترب (Torob)»

متن این کارت دربارهٔ ثبت فروشگاه در `torob.com/sell` و مسیر فید است: `/api/torob/feed`. این مسیر یک خروجی XML می‌دهد که **قیمت‌ها در آن به ریال** است (نه تومان) — چون قرارداد ترب ریالی است.

### دکمه و اعتبارسنجی

دکمه: «ذخیره تنظیمات» → `PUT /api/admin/settings`.

اعتبارسنجی سمت کاربر: «درگاه پیش‌فرض باید یکی از درگاه‌های فعال باشد.» — یعنی نمی‌توان درگاهی را پیش‌فرض کرد که کلید «فعال»ش خاموش است.

موفقیت: «ذخیره شد» / «تنظیمات درگاه‌های پرداخت به‌روزرسانی شد.»

### پنجرهٔ «حذف کاربر» — سه حالت

سیستم پیش از حذف، فعالیت کاربر را می‌شمارد و بر اساس آن یکی از سه حالت را نشان می‌دهد:

**حالت ۱ — کاربر فعالیت دارد:** هشدار نارنجی با عنوان «این کاربر فعالیت ثبت‌شده دارد» و متن «{n} مورد فعالیت برای این کاربر ثبت شده است و به همین دلیل حذف نمی‌شود؛ فقط می‌توانید حسابش را غیرفعال کنید.» به‌همراه «کاربر غیرفعال نمی‌تواند وارد شود، اما سابقه‌اش دست‌نخورده می‌ماند و هر زمان می‌توانید فعالش کنید.» — تنها دکمه: «غیرفعال کردن».

**حالت ۲ — بررسی فعالیت شکست خورده:** هشدار قرمز «بررسی فعالیت‌های این کاربر ناموفق بود؛ برای جلوگیری از حذف ناخواسته، حذف انجام نشد. صفحه را دوباره باز کنید.» — تنها دکمه: «بستن». این حالت عمداً محافظه‌کارانه است: خطا به «حذف» ترجمه نمی‌شود.

**حالت ۳ — کاربر بی‌فعالیت:** «این کاربر هیچ فعالیتی در سایت ثبت نکرده است، پس حذفش بی‌خطر است.» — دکمه: «حذف».

**قاعدهٔ محافظت از خود:** کاربر نمی‌تواند حساب خودش را حذف یا غیرفعال کند (دکمه‌ها برای ردیف خودش غیرفعال‌اند).

پیام‌های فعال/غیرفعال: «حساب فعال شد» / «{name} دوباره می‌تواند وارد شود.» و «حساب غیرفعال شد» / «{name} تا فعال‌سازی دوباره نمی‌تواند وارد شود.»

**خانوادهٔ خطاها** (سه نوع): «درگاه پرداخت» (آبی نیلی)، «پنل پیامکی» (بنفش)، «شاهکار» (فیروزه‌ای). این ردیف‌ها نام درگاه یا پنلی را که پاسخ داده نشان می‌دهند و با باز شدن، **پاسخ خام API** را در یک بلوک کد چپ‌به‌راست نمایش می‌دهند.

**خانوادهٔ رخدادهای کارمندان** (سه نوع): «کاربران» (آبی)، «قیمت‌ها» (نارنجی)، «سفارش‌ها» (فیروزه‌ای). این ردیف‌ها نام کارمند مسئول را نشان می‌دهند و با باز شدن، **جزئیات تغییر** (مقدار قبل و بعد) را به‌صورت متن فارسی راست‌به‌چپ نمایش می‌دهند.

### کنترل‌ها

| کنترل | برچسب | گزینه‌ها |
| --- | --- | --- |
| انتخابی | «نوع لاگ» | گروه «نمایش» → «همه لاگ‌ها»؛ گروه «رخدادهای کارمندان» → سه نوع بالا؛ گروه «خطاهای سیستمی» → سه نوع بالا |
| دکمه | «پاک کردن لاگ‌ها» (قرمز) | وقتی جدول خالی است غیرفعال است |

### ستون‌های جدول

«تاریخ و ساعت» (مونواسپیس)، «نوع» (نشان رنگی)، «درگاه / پنل» (برای ردیف کارمندی «—»)، «کاربر» (برای ردیف خطا «—»)، «عملیات»، «پیام»، و ستون آخر با فلش بازکردن.

برچسب‌های ستون «عملیات»: «شروع پرداخت»، «تأیید تراکنش»، «پیامک فاکتور»، «پیامک اطلاع‌رسانی ارسال»، «پیامک لینک پرداخت»، «تطبیق شاهکار»، «ایجاد»، «ویرایش»، «حذف»، «تغییر دسترسی»، «تغییر نقش»، «تغییر قیمت»، «تغییر وضعیت»، «تغییر وضعیت حساب».

راهنمای فلش بازکردن: «نمایش جزئیات تغییر» یا «نمایش پاسخ API». برچسب داخل ردیف بازشده: «جزئیات تغییر:» یا «پاسخ API مقصد:».

حالت خالی: «لاگی ثبت نشده است.» / «در حال بارگذاری…».

### پنجرهٔ «پاک کردن لاگ‌ها»

اگر فیلتر روی «همه لاگ‌ها» باشد: «همه لاگ‌های سیستمی پاک شوند؟ این کار قابل بازگشت نیست.» وگرنه: «لاگ‌های «{label}» پاک شوند؟ این کار قابل بازگشت نیست.» دکمه‌ها: «انصراف» / «پاک شود».

موفقیت: «انجام شد» / «لاگ‌های سیستمی پاک شد.» — خطا: «پاک کردن لاگ‌ها ناموفق بود.»

**نکتهٔ امنیتی:** گذرواژه‌ها **هرگز** در لاگ نوشته نمی‌شوند.

# ۵. فروشگاه (بخش مشتری)

## ۵٫۱ ساختار کلی

فروشگاه کاملاً عمومی است. صفحهٔ اصلی `/` هم‌زمان **فهرست کالاها** و **صفحهٔ اصلی قالب** است — صفحهٔ جداگانه‌ای برای فهرست وجود ندارد و `/shop` بدون پارامتر فقط به `/` ریدایرکت می‌کند.

فروشگاه به‌صورت `force-dynamic` رندر می‌شود؛ یعنی هر بازدید تازه از پایگاه‌داده می‌خواند و تغییرات قیمت یا محتوا بی‌درنگ دیده می‌شوند.

## ۵٫۲ جست‌وجو و عنوان صفحه

عنوان تب مرورگر و توضیحات متا از «مشخصات سایت» خوانده می‌شوند. اگر توضیحی تنظیم نشده باشد، متن پیش‌فرض «محصولات موجود در فروشگاه را ببینید.» استفاده می‌شود. زبان اعلامی Open Graph روی `fa_IR` تنظیم است.

صفحهٔ اصلی یک داده ساخت‌یافتهٔ `ItemList` هم منتشر می‌کند که فهرست کالاها را برای موتورهای جست‌وجو توصیف می‌کند (حداکثر ۲۰ قلم اول).

## ۵٫۳ هدر فروشگاه

هدر همهٔ قالب‌ها یک اسکلت مشترک دارد:

| عنصر | متن / برچسب |
| --- | --- |
| نام برند | از «نام سایت» — اگر خالی باشد، حرف اول نام یا «ف» در نشان برند می‌نشیند |
| ناوبری | `aria-label="ناوبری فروشگاه"` |
| جست‌وجو | جای‌نگهدار «جستجوی محصول…» با `aria-label="جستجوی محصول"` |

آیکون‌های سمت چپ هدر: «سبد خرید» (با نشان تعداد)، «کیف پول»، و «منوی حساب کاربری».

## ۵٫۴ بخش‌های صفحهٔ اصلی

بخش‌هایی که رندر می‌شوند به قالب فعال بستگی دارند (فصل ۴٫۳). هر بخش یک لنگر (anchor) دارد تا فوتر و منو بتوانند به آن لینک بدهند: `#bestSellers`، `#latestPosts`، `#newsletter`، `#giftIdeas` و مانند این‌ها.

**جای‌گذاری کالا در بخش‌ها:** هر کالا و هر دسته‌بندی می‌تواند به بخش‌های خاصی «سنجاق» شود (فیلد `placements` با ساختار `{ themeId: [sectionId] }`). اگر کالایی هیچ سنجاقی نداشته باشد، در همهٔ بخش‌ها دیده می‌شود. اگر سنجاق داشته باشد، فقط در بخش‌های خودش **و بخش‌های دسته‌بندی‌هایش** ظاهر می‌شود (اجتماع هر دو).

## ۵٫۵ کارت محصول

هر کارت محصول در همهٔ قالب‌ها یک اسکلت مشترک دارد:

| عنصر | متن |
| --- | --- |
| قیمت | برای کالای بدون قیمت: «—» |
| وضعیت موجودی | «موجود» یا «ناموجود» |

قیمت‌ها با جداکنندهٔ هزارگان فارسی و ارقام فارسی نمایش داده می‌شوند (بدون `Intl`، به‌صورت رشته‌ای).

## ۵٫۶ صفحهٔ کالا — `/shop/{slug}`

عنوان تب مرورگر: نام کالا. اگر کالا نباشد: «محصول یافت نشد» با متن «این محصول وجود ندارد یا نمایش آن پنهان است.» (کالاهای پنهان ۴۰۴ می‌دهند، نه ۴۰۳ — تا وجودشان لو نرود.)

| عنصر | متن / برچسب |
| --- | --- |
| گالری | `aria-label="تصویر {n} از {n}"` برای هر تصویر |
| وضعیت | «موجود در این نوع» (اگر نوع انتخابی موجود باشد) یا «موجود» یا «ناموجود» |
| برچسب قیمت | «قیمت محصول» یا «قیمت نوع» (وقتی نوع انتخاب‌شده قیمت خودش را دارد) |
| تعداد | دو دکمه با `aria-label="کاهش تعداد"` و `aria-label="افزایش تعداد"` |
| دکمهٔ افزودن | «افزودن به سبد خرید» — وقتی موجودی صفر است، برچسب «ناموجود» و دکمه غیرفعال |
| مشخصات | جداکننده با برچسب «مشخصات» |

پس از افزودن به سبد: پیام «به سبد خرید افزوده شد».

## ۵٫۷ سبد خرید (کشوی کناری)

سبد خرید یک `Drawer` از سمت راست با عنوان «سبد خرید» است — **صفحهٔ `/cart` وجود ندارد**.

| عنصر | متن / برچسب |
| --- | --- |
| حذف یک قلم | `aria-label="حذف {نام کالا}"` |
| کاهش / افزایش | `aria-label="کاهش تعداد"` / `aria-label="افزایش تعداد"` |
| متن توضیح | «با ادامه خرید، اقلام بالا به این سفارش افزوده می‌شوند:» یا «این سفارش تا پرداخت در سبد شما می‌ماند:» |
| حذف از سفارش | `aria-label="حذف {نام کالا} از سفارش"` |
| دکمهٔ اصلی | «ادامه و پرداخت» (کاربر واردشده) یا «ورود و ادامه خرید» (مهمان) |

### پیام‌های سبد

| حالت | عنوان | متن |
| --- | --- | --- |
| حذف موفق | «از سفارش حذف شد» | — |
| حذف ناموفق | «حذف قلم ناموفق بود» | متن خطای سرور یا «لطفاً دوباره تلاش کنید.» |
| خطای شبکه | «ارتباط برقرار نشد» | «اتصال خود را بررسی کنید و دوباره تلاش کنید.» |
| ثبت ناموفق | «ثبت سفارش ناموفق بود» | متن خطای سرور یا «لطفاً دوباره تلاش کنید.» |
| ثبت موفق (ادغام) | «سبد به سفارش پرداخت‌نشده شما افزوده شد» | — |
| ثبت موفق (تازه) | «سفارش شما ثبت شد» | — |

**قاعدهٔ مهم:** اگر مشتری از قبل یک سفارش پرداخت‌نشده داشته باشد، اقلام سبد **به همان سفارش اضافه می‌شوند** و سفارش تازه‌ای ساخته نمی‌شود. به همین دلیل در سبد دو بخش جدا دیده می‌شود: اقلام تازهٔ سبد و اقلام سفارش پرداخت‌نشدهٔ قبلی (که با دکمهٔ حذف جداگانه‌ای قابل برداشتن‌اند).

## ۵٫۸ پنجرهٔ ورود — `AuthModal`

وقتی مهمی وارد شدن لازم باشد، یک پنجرهٔ گفتگو باز می‌شود (نه انتقال به صفحهٔ جدا):

| فیلد | برچسب | جای‌نگهدار |
| --- | --- | --- |
| موبایل | «شماره موبایل» | `۰۹۱۲۱۲۳۴۵۶۷` |
| گذرواژه | «گذرواژه» | «گذرواژه خود را وارد کنید» |

خطا: عنوان «ورود انجام نشد» با متن خطای سرور.

## ۵٫۹ فوتر فروشگاه

فوتر همهٔ قالب‌ها یک اسکلت مشترک دارد:

| ستون | منبع |
| --- | --- |
| برند | «نام سایت» + «درباره ما» (یا متن پیش‌فرض «فروشگاه اینترنتی — خرید آسان، ارسال سریع.») |
| دو ستون لینک | هر قالب ستون‌های خودش را دارد (جدول زیر) |
| «تماس با ما» | «تلفن: … · ایمیل: … · نشانی: …» — هر کدام که در مشخصات سایت پر شده باشد |
| نشان‌ها | «نشان اینماد» و «نشان رسانه» (در صورت بارگذاری در مشخصات سایت) |
| نوار پایانی | «© {نام سایت} — تمامی حقوق محفوظ است.» |

### ستون‌های فوتر به تفکیک قالب

**BeautyShop:** «دسترسی سریع» (خانه، پرفروش‌ترین‌ها، مجله، خبرنامه) و «راهنمای خرید» (نحوه ثبت سفارش، رویه ارسال سفارش، شرایط بازگشت کالا) — به‌همراه ردیفی از چیپ‌های شبکه‌های اجتماعی که با «اینستاگرام» شروع می‌شود.

**DigiMarket:** «دسته‌بندی‌ها» و «پشتیبانی».

**DigiShop:** «خرید هدیه» و «خدمات مشتریان».

**SoftKala:** «دسته‌بندی‌ها» و «پشتیبانی فنی».

## ۵٫۱۰ صفحهٔ پرداخت با لینک — `/pay/{token}`

این صفحه **عمومی** است و نیازی به ورود ندارد. ورود به آن فقط با یک توکن یکتا در نشانی ممکن است (`Order.paymentToken`). کاربردش: مشتری می‌تواند لینک فاکتور را برای شخص دیگری پیامک کند تا او پرداخت کند.

| حالت | نتیجه |
| --- | --- |
| توکن نامعتبر یا حذف‌شده | عنوان «فاکتور یافت نشد» / «این لینک پرداخت معتبر نیست یا حذف شده است.» |
| توکن معتبر | نام سایت + فرم پرداخت با همان انتخابگر درگاه تسویه‌حساب + اقلام فاکتور |

اطلاعات نمایش‌داده‌شده: شمارهٔ سفارش، تاریخ، وضعیت، اقلام، مبلغ، تخفیف، کد تخفیف، هزینهٔ ارسال و روش تحویل.

**قید مهم:** پرداخت‌کنندهٔ لینک **نمی‌تواند سفارش را تغییر دهد** — فقط می‌بیند و پرداخت می‌کند.

# ۶. ویجت پشتیبانی فروشگاه (تفصیلی)

ویجت پشتیبانی یک دکمهٔ شناور گوشهٔ صفحهٔ فروشگاه است که گفتگوی مشتری با پشتیبان را بدون ترک صفحه باز می‌کند.

## ۶٫۱ شرط نمایش

ویجت **فقط** وقتی روی صفحه می‌آید که هر دو شرط برقرار باشد:

۱. در «تنظیمات ← پشتیبانی»، کلید «فعال بودن پشتیبانی آنلاین» روشن باشد.
۲. بازدیدکننده یا مهمان باشد یا نقشی جز مشتری نداشته باشد. یعنی **کارمندان واردشده ویجت را نمی‌بینند** (چون خودشان پشتِ میز پشتیبان‌اند).

ویجت در سه جا رندر می‌شود: صفحهٔ اصلی فروشگاه (`/`)، صفحهٔ کالا (`/shop/{slug}`)، و هر صفحه‌ای که قالب فروشگاه را می‌کشد. **در ناحیهٔ حساب کاربری مشتری (`/account/support`) ویجت شناور وجود ندارد** — آنجا گفتگو در خودِ صفحه است.

## ۶٫۲ دکمهٔ شناور

| ویژگی | مقدار |
| --- | --- |
| شکل | دکمهٔ گرد ۵۲ پیکسلی |
| رنگ | فیروزه‌ای توپر |
| آیکون | هدست |
| برچسب دسترس‌پذیری | «گفتگو با پشتیبانی» |
| لایه | روی همهٔ محتوای صفحه (z-index بالا) |

### نشان پیام خوانده‌نشده

اگر پیام تازه‌ای از پشتیبان آمده باشد که مشتری ندیده، یک نشان قرمز روی دکمه ظاهر می‌شود:

| حالت | نمایش |
| --- | --- |
| صفر | نشان پنهان |
| ۱ تا ۹ | همان عدد |
| بیشتر از ۹ | «۹+» |

## ۶٫۳ جای آیکون (چهار گوشه)

بر اساس گزینهٔ «جای آیکون» در تنظیمات، دکمه در یکی از چهار گوشهٔ صفحه می‌نشیند: «پایین-چپ» (پیش‌فرض)، «پایین-راست»، «بالا-چپ»، «بالا-راست».

**نکتهٔ فنی ظریف:** فاصله از لبه‌ها به‌صورت **فیزیکی** (`left`/`right`) اعمال می‌شود، نه منطقی (`insetInlineEnd`). دلیل: ادمین «گوشهٔ صفحه» را انتخاب می‌کند و اگر از ویژگی منطقی استفاده می‌شد، در صفحهٔ چپ‌به‌راست گوشه آینه می‌شد و انتخاب ادمین بی‌معنا می‌شد.

## ۶٫۴ انیمیشن ورود

بر اساس گزینهٔ «انیمیشن نمایش»، دکمه یکی از این پنج حالت را دارد:

| گزینه | رفتار |
| --- | --- |
| «بدون انیمیشن (نمایش یکباره)» | دکمه بی‌درنگ و بدون حرکت ظاهر می‌شود |
| «محو شدن» (پیش‌فرض) | از شفافیت صفر به یک می‌آید |
| «بزرگ شدن» | از کوچک به اندازهٔ کامل بزرگ می‌شود |
| «سریدن از لبه» | از لبهٔ همان گوشه به داخل می‌سرید — در گوشه‌های پایین از پایین، در گوشه‌های بالا از بالا |
| «پاپ از گوشه» | از همان گوشهٔ انتخابی با جهش کوچک بیرون می‌آید |

مدت انیمیشن ۲۲۰ میلی‌ثانیه است. همهٔ انیمیشن‌ها از کامپوننت ترنزیشن خود Mantine می‌آیند، پس هیچ CSS دست‌ساز یا کتابخانهٔ اضافه‌ای در کار نیست.

## ۶٫۵ تأخیر نمایش

گزینهٔ «تأخیر نمایش آیکون (ثانیه)» تعیین می‌کند چند ثانیه پس از باز شدن صفحه، دکمه ظاهر شود:

| مقدار | رفتار |
| --- | --- |
| ۰ (پیش‌فرض) | دکمه از همان ابتدا هست |
| ۳ مثلاً | دکمه سه ثانیه هیچ‌جا نیست، بعد با انیمیشن انتخابی وارد می‌شود |

کاربرد: اگر بخواهید بازدیدکننده اول محتوای صفحه را ببیند و بعد ویجت سر راهش سبز شود.

## ۶٫۶ حباب پیام خوش‌آمد

اگر گزینهٔ «نمایش پیام خوش‌آمد» روشن باشد، کنار دکمه یک حباب با متن خوش‌آمد (همان متن کارت «متن خوش‌آمد») ظاهر می‌شود.

| ویژگی | رفتار |
| --- | --- |
| جای حباب | در گوشه‌های **پایین**، بالای دکمه. در گوشه‌های **بالا**، زیر دکمه |
| هم‌ترازی | در گوشه‌های چپ از لبهٔ چپ، در گوشه‌های راست از لبهٔ راست |
| حداکثر عرض | ۲۴۰ پیکسل |
| بسته شدن دستی | یک دکمهٔ بستن با برچسب «بستن پیام» روی خود حباب — کلیک روی آن فقط حباب را می‌بندد و گفتگو را باز نمی‌کند |
| کلیک روی حباب | گفتگو را باز می‌کند (خود حباب هم دکمه است، با برچسب «باز کردن گفتگو با پشتیبانی») |
| بسته شدن خودکار | بر اساس گزینهٔ «مدت نمایش پیام خوش‌آمد (ثانیه)» — مقدار ۰ یعنی تا بستن دستی باز می‌ماند |
| تکرار | **در هر نشست مرورگر فقط یک‌بار** |

**قاعدهٔ «یک‌بار در نشست»:** حباب یک سلامِ یک‌باره است، نه یک پیام هر صفحه‌ای. وقتی یک‌بار نمایش داده شد، در `sessionStorage` مرورگر علامت می‌خورد و تا بسته شدن آن تب یا مرورگر دیگر تکرار نمی‌شود. اگر مرورگر `sessionStorage` را مسدود کرده باشد، خطا بی‌صدا رد می‌شود و صفحه سالم کار می‌کند. علامتگذاری **پیش از** نمایش انجام می‌شود تا اگر صفحه در میانهٔ راه دوباره رندر شود، حباب دوباره سبز نشود.

## ۶٫۷ پنجرهٔ گفتگو (Drawer)

با کلیک روی دکمه، یک کشوی کناری از **سمت راست** با عرض متوسط باز می‌شود:

| ویژگی | مقدار |
| --- | --- |
| عنوان | «پشتیبانی آنلاین» |
| دکمهٔ بستن | با برچسب «بستن» |
| متن معرفی | «گفتگوی شما با پشتیبان سایت — پاسخ‌ها همین‌جا نمایش داده می‌شوند.» |
| ارتفاع ناحیهٔ گفتگو | ۳۶۰ پیکسل |

**نکتهٔ مهم:** کشو همیشه در صفحه «سوار» می‌ماند (حتی وقتی بسته است). دلیل: اگر از صفحه برداشته شود، نشان پیام خوانده‌نشده روی دکمه دیگر به‌روز نمی‌شود و مشتری پیام تازه را نمی‌بیند.

## ۶٫۸ فرم شروع گفتگوی مهمان

مهمان (بدون حساب) پیش از هر چیز این فرم را می‌بیند:

| عنصر | متن |
| --- | --- |
| هشدار آبی | متن خوش‌آمدِ تنظیمات |
| راهنما | «برای شروع گفتگو، نام و شماره موبایل خود را وارد کنید تا پشتیبان بتواند پاسخ دهد.» |
| فیلد نام | «نام و نام خانوادگی» |
| فیلد موبایل | «شماره موبایل» |
| متن پیام | «پیام شما» — جای‌نگهدار «سؤال یا مشکل خود را بنویسید…» — حداکثر ۲۰۰۰ نویسه |
| دکمه | «ارسال پیام» |

دکمهٔ «ارسال پیام» غیرفعال می‌ماند تا هر سه شرط برقرار شود: نام حداقل ۲ نویسه، موبایل دقیقاً ۱۱ رقم، و متن پیام غیرخالی.

**مهمان‌ها نیازی به ثبت‌نام ندارند.** یک کوکی مهمان ۳۰ روزه می‌سازد تا اگر بعداً برگشت، گفتگویش را ببیند.

## ۶٫۹ ساخت تیکت تازه (مشتری واردشده)

برای مشتری واردشده که می‌خواهد تیکت تازه بسازد:

| عنصر | متن |
| --- | --- |
| عنوان | «تیکت جدید» |
| دکمهٔ بازگشت | «بازگشت» |
| فیلد | «موضوع» — جای‌نگهدار «مثلاً: پیگیری سفارش» — حداکثر ۱۲۰ نویسه |
| متن | «متن پیام» — حداکثر ۲۰۰۰ نویسه |
| دکمه | «ارسال تیکت» |

دکمه غیرفعال می‌ماند تا موضوع حداقل ۲ نویسه و متن پیام غیرخالی باشد. دکمهٔ «تیکت جدید» **فقط برای مشتری واردشده** دیده می‌شود؛ مهمان مستقیم فرم شروع گفتگو را می‌گیرد.

اگر وضعیت تیکت «بسته شده» باشد، به‌جای کادر پاسخ یک هشدار خاکستری نشان داده می‌شود: «این تیکت بسته شده است — برای ادامه، تیکت تازه‌ای بسازید.» — یعنی مشتری نمی‌تواند در تیکت بسته پیام بگذارد.

## ۶٫۱۲ به‌روزرسانی خودکار

گفتگوی ویجت خودش را تازه می‌کند تا مشتری مجبور نباشد صفحه را رفرش کند:

| حالت | فاصلهٔ تازه‌سازی |
| --- | --- |

همین ریتم در پنل پشتیبان هم برقرار است (فصل ۳٫۶) تا دو طرف گفتگو بدون رفرش دستی همدیگر را ببینند.

هستهٔ گفتگو بین **ویجت فروشگاه** و **صفحهٔ `/account/support`** مشترک است — همان کامپوننت، فقط با ارتفاع متفاوت (۳۶۰ در ویجت، ۴۲۰ در صفحه). نتیجه: پیام‌ها، وضعیت‌ها، فهرست‌ها و قواعد هر دو جا یکی هستند و مشتری تفاوتی حس نمی‌کند.

## ۷٫۷ پرداخت سفارش — `/account/checkout`

عنوان: «پرداخت سفارش {شناسه}». یک فرآیند سه‌مرحله‌ای عمودی.

### کارت فاکتور

عنوان «اقلام سفارش». هر قلم با نام، «× {تعداد}» و مبلغ خط. سپس جداکننده و خطوط جمع: «جمع سفارش»، تخفیف (با نشان کد)، هزینهٔ ارسال، و در پایان «مبلغ قابل پرداخت» به‌صورت برجسته.

### فیلد کد تخفیف

جای‌نگهدار «کد تخفیف دارید؟» با دکمهٔ بررسی. پس از اعمال، نشان سبز کد تخفیف با دکمهٔ «حذف کد» ظاهر می‌شود. خطاها: «کد تخفیف را وارد کنید.» / «بررسی کد تخفیف ناموفق بود.» / «ارتباط با سرور برقرار نشد. اتصال خود را بررسی کنید.»

### مرحلهٔ ۱ — «آدرس تحویل»

توضیح: «نشانی ارسال سفارش را انتخاب کنید». فهرست آدرس‌های ذخیره‌شده به‌صورت دکمه‌های رادیویی با عنوان آدرس. زیر آدرس انتخاب‌شده: «{نام گیرنده} — {نشانی} (کدپستی {کد})».

اگر آدرسی نباشد: «هنوز آدرسی ذخیره نکرده‌اید.» و پیوند «+ افزودن آدرس جدید».

موفقیت پرداخت: «سفارش پرداخت شد». خطاها: «شروع پرداخت ناموفق بود.» / «پاسخ پرداخت نامعتبر بود.» / «ارتباط با سرور برقرار نشد. اتصال خود را بررسی کنید.»

# ۸. مدل داده و مرجع API

## ۸٫۱ چیدمان ماژول‌ها

کد سامانه عمداً به دو نیمهٔ جدا تقسیم شده و این تقسیم‌بندی **قاعده** است، نه سلیقه:

**نیمهٔ امن برای کلاینت** (نه Prisma، نه React): `lib/constants.ts` (نام و عمر کوکی‌ها)، `lib/nav-permissions.ts` (کاتالوگ منوها)، `lib/order-status.ts`، `lib/support-status.ts`، `lib/system-log-defs.ts`، `lib/format.ts`، `lib/login-method.ts`، `lib/price-adjust.ts`، `lib/themes.ts`.

**نیمهٔ سروری** (Prisma و پایگاه‌داده): `lib/orders.ts`، `lib/customers.ts`، `lib/products.ts`، `lib/wallet.ts`، `lib/support.ts`، `lib/settings.ts`، `lib/system-logs.ts`، `lib/auth.ts`، `lib/api-auth.ts`، `lib/session.ts`.

قاعدهٔ عملی برای افزودن کد تازه: **اگر کد به Prisma یا React نیاز دارد، سمت سرور است؛ وگرنه سمت کلاینت.** نقض این قاعده یعنی پایگاه‌داده به باندل مرورگر کشیده می‌شود.

**استثنای مهم:** `lib/session.ts` هم در Edge (پروکسی) و هم در Node اجرا می‌شود و به همین دلیل **فقط** از Web Crypto و `btoa`/`atob` استفاده می‌کند. وارد کردن `node:crypto` به این فایل، پروکسی را از کار می‌اندازد.

## ۸٫۳ قراردادهای ذخیره‌سازی

چون SQLite ستون `Json` ندارد، هر دادهٔ ساخت‌یافته **رشتهٔ JSON** است که در کد اعتبارسنجی می‌شود:

| فیلد | محتوا | نقطهٔ اعتبارسنجی |
| --- | --- | --- |
| `Product.props` | ویژگی‌های پویا کالا | `lib/products.ts` |
| `Product.placements` و `Category.placements` | `{ themeId: [sectionId] }` — سنجاق به بخش‌های قالب | `lib/theme-settings.ts` |
| `Order.itemsJson` | `[{productId, variantId, name, qty, unitPrice}]` | `lib/orders.ts` |
| `Role.permissions` | فهرست مسیرهای منویی | `lib/nav-permissions.ts` |
| `ThemeConfig.config` | پالت، بخش‌ها و عنوان‌های سفارشی | `lib/theme-settings.ts` |
| `MetaTag.content` | مقدار کد متا — **فقط شناسه‌های مجاز** | `lib/meta-tags.ts` |
| فهرست خبرنامه | ایمیل‌های ثبت‌شده | `app/api/newsletter` |

سه قاعدهٔ سراسری دیگر:

- **پول همیشه عدد صحیح تومان است.** هیچ‌جا اعشار یا ریال ذخیره نمی‌شود (تنها استثنا: خروجی فید ترب که به ریال است، چون قرارداد ترب ریالی است).
- **تاریخ‌ها از پیش قالب‌بندی‌شده‌اند.** `Order.date` یک رشتهٔ جلالی آماده است و `SystemLog.createdAt` هم هنگام خواندن به رشتهٔ `yyyy/MM/dd HH:mm` تبدیل می‌شود. دلیل: تطابق هیدریشن.
- **`datasource url` به‌صورت hardcode** روی `file:../data/app.db` است تا CLI، seed و اجرای برنامه همیشه یک فایل را ببینند و نیاز به `.env` نباشد.
